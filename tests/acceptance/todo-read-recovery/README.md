# 对话待办的安静读取恢复

基线 `2c3b832`。先增加“可恢复失败不能提前报错”的断言，复现待办 GET 第一次返回 503 就立即显示错误的问题。

## 改动

- 待办读取复用资源存储的有界指数退避、抖动、单次八秒超时和共同一分钟期限；最多六次尝试，期间保留已有计划。移除待办单独维护的重试计数器、计时器及读取代次，避免两套实现漂移。
- 事件已经到达而待办投影尚未同步时，继续纯读取，和网络失败共用一个预算。预算耗尽才显示准确的最终提示；明确的权限拒绝、会话不存在或畸形响应不盲目重试，不显示不可用旧列表。
- 读取范围独立保存，永久拒绝丢弃旧列表之后，正式重试仍能读取原会话。普通刷新合并待处理请求并保留耗尽提示，显式重试及新计划事件立即重新读取。
- 更新的计划事件取消旧读取；恢复历史先清除原单调事件下限，允许零事件的空计划，丢弃恢复前迟到的结果。相同后台快照不重新发布状态或重建控件。
- 最终待办读取提示接入已有唯一可重试提示区域，覆盖中英俄文，不弹错误 toast，不重放实际计划工具。

## 实际打包页面

`manual_todo_read_recovery_qa.py` 使用普通设置 API 配置回环模型，通过正式输入框连续运行三个真实 `mdo.todo` 工具。测试接缝只返回有界的 GET 503，不修改实际工具、投影、会话或模型事件。

先创建 0/2 计划，模拟两次读取失败后实际自动恢复到 1/2，没有错误提示且输入保留，见 `automatic-faults.json` 和 `automatic-restored.json`。随后第三次计划工具已把真实计划更新到 2/2，六次 GET 失败期间仍显示原 1/2；`exhaustion-pending.json` 记录原列表、主输入框焦点、完整草稿和零错误提示。耗尽时只出现一处准确的“暂时无法读取待办列表”提示，仍保留原计划和草稿，见 `final-read-notice.json` 与截图。

在后台复查的等待期内点击正式“重试读取”，页面立即恢复真实 2/2，焦点返回主输入框，草稿保留；随后发送该草稿正常续聊。`native-runs.json` 记录四轮对话、七次模型请求、三个成功的计划工具和零最终模型错误，最终计划的两项均已完成；`continued.json` 与截图核对完整页面结果。

## 回归与构建

- 85 项 Node 检查通过，包括待办的 11 项针对性检查及前一阶段的询问/审核/运行/任务、读取恢复、模型错误与设置回归。可控时钟验证六次预算、投影/网络混合失败、挂起读取超时和取消；历史边界、会话切换、相同快照与永久拒绝的手动恢复亦覆盖。
- 正式待办组件的九项实际浏览器检查通过：安静保留计划、自动恢复、保留行元素/折叠/焦点、迟到错误隔离、取消旧重试、清空计划及焦点归还，见 `components.json`。夹具同时修复静态服务下语言包路径的问题。
- 三个相关干净前端合约通过：模块闭包、增量任务输出和设置自动保存。
- 独立 Windows 候选 `.build/conversation-acceptance/mdo-todo-reads-final.exe` 由干净基线加本阶段改动生成，六个内置生产文件的实际 HTTP 返回与隔离源码逐字节一致，见 `build.json`。原生源代码未变，复用匹配的已验证宿主；测试接缝及其他未提交改动均不在候选中。

复现：准备 unity 后启动脚本并打开打印 URL，发送 `baseline`；调用隔离端点 `/api/v1/qa-todo-arm/2` 后发送 `update`，观察自动恢复；调用 `/api/v1/qa-todo-arm/6` 后发送 `update-final`，观察安静等待与最终提示，点击正式重试并续聊。创建打印的 stop 文件清理实例，最长六分钟。
