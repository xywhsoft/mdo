## 实际问题与行为

旧候选的一次“创建计划”点击在成功回复头丢失后，被浏览器重发为两个 POST，两个原生 201 和两个不同编号的同名计划。`baseline-*` 为实际旧打包页、原生目录和 HTTP 记录，代理自身不重放请求。

新建表单现在预先保留编号；同一个保存意图只派发一次写操作，丢失或损坏的回复只触发原编号 GET。原生服务已有的编号唯一性和版本条件保护浏览器重发，未引入数据库或持久回执。创建、修改、暂停、删除核对同一宿主的完整结果；明确的存储、数量、权限拒绝不变成“等待确认”。自动核对有八秒请求、一分钟总期限和六次读取上限。

| 创建成功回复头丢失 | 两个相同编号的传输 POST 得到 201、409；只生成一项计划，页面无错误 |

| 立即运行成功正文暂扣 | 一个启动 POST、一次实际执行；八秒后只有一条“先查看执行历史”的最终提示，历史一条成功记录 |
| 修改已保存，原编号 GET 连续六次 503 | 退避间隔 0.594、1.094、2.187、4.750、9.172 秒；一条表单最终提示，字段保留且按钮恢复 |

第二个计划的首次创建暂扣也正常恢复；那次读取故障装置设置得太晚，不能算作六次失败验收。真正六次失败发生在其后的一次修改，独立检查按该 PUT 的时刻核算，保留全部记录。

删除由生产 `createScheduleWriter` 配合实际原生 API 适配器检查：DELETE 成功回复断连后只用详情 404 和同代目录确认不存在，一个 DELETE；另一个隔离计划正常清理。该证据是 API 检查，**不是浏览器删除确认界面验收**。所有数据均为本轮隔离 Home 创建的测试数据。
