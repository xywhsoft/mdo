# 停止请求的超时、确认与错误清除

基线 `4a526a0`。停止控制器原先没有 HTTP 请求超时或连接正常时的总等待上限：一个不返回的 DELETE/GET 会让停止永久忙碌。目标变化后也不能取消正在等待的传输。补上单次八秒、连接期间一共一分钟的限制，按指数退避只读确认原运行，得到明确状态后才决定是否重试幂等停止。已知离线时保留停止意图，等待恢复连接；不重放新运行、模型或工具请求。

过程中还发现，停止未确认提示在稍后明确停止或结束时仍留在输入框上方。现在错误携带所属运行，只有同一项目、会话、运行的权威取消或结束状态能清除它，其他错误不会被顺带清除。

## 回归

新增检查覆盖挂起的停止与读取、全周期耗尽、长时间已知离线、目标清理与迟到回复、HTTP 开始前取消、真实 API 适配器的 AbortSignal，以及匹配运行状态的错误清除。新增错误清除检查之前，旧控制器的 20 项检查为 12 通过、8 失败；最终停止控制器 21 项全部通过。与运行序列、恢复动作和语言检查一并执行为 51 项通过，另有 4 项前端契约通过。

```powershell
node --test tests/test_run_stop_controller.mjs tests/test_frontend_session_runtime.mjs tests/test_recovery_action.mjs tests/test_frontend_i18n.mjs
```

虚拟时钟明确验证一分钟上限，期间不调用错误回调，耗尽时只调用一次。浏览器快照是在停止后 72.327 秒采集，证明最终提示存在，不能拿快照时间冒充提示首次出现的精确时刻。

## 真实打包验证

隔离工作树基于上述提交，使用固定 xs `3232f7b8efb02fdd6bf63a508ed1e69654d6759c` 和真实构建收据。没有把根目录的其他在开发变更或 QA 注入代码打包。`build.json` 记录最终候选 SHA-256、大小和六个实际 HTTP 资源与源码逐字节一致。候选也包含前一阶段恢复确认的运行锁取消修复。

`manual_run_stop_deadline_qa.py` 启动真实打包程序，仅通过回环代理延迟或拒绝 HTTP，请求接入本地确定性模型。WebSocket 不可用，验证走实际状态轮询。

- 第一遍：真实停止已接受，DELETE 回复和一次运行 GET 各延迟十二秒。全程只执行一次 DELETE；后续运行读取在停止约九秒后开始，证明前一个等待已释放。草稿保留，下一条对话成功。证据在 `proof-first-pass.json`、`browser-first-pass.json`、`stopped-draft.png`。这遍也暴露了成功后旧错误不消失，随后修复。
- 最终候选：停止在到达原生程序前返回 503，运行与目录读取持续不可用。原生停止次数为零，最终只出现一个停止未确认 alert，草稿保留。解除故障后，状态轮询明确收到此前运行已自然结束，旧错误自动消失，无需再点停止；后续输入成功。`proof.json` 确认两条输入各调用模型一次、零最终模型错误、零活跃运行、空队列和空提交记录。

第一遍使用较长模型等待，`stream-stop` 有两次模型 HTTP 调用，原因未在本阶段定位，不能宣称该遍模型没有重试。最终夹具改为四十五秒自然完成，避免用模型空闲超时检验停止确认；最终各一次模型调用有实际记录。
