# 后台会话刷新挂起与输入完整性复测

基线为 `50a0f8e`，加本阶段后台元数据修复。之前后台单独调用 `readSession`，没有超时和取消；一个挂起的 GET 会一直占据该会话的进行中标记，后续刷新复用同一未完成请求。前台详情此前已有恢复机制，但不能消除这个独立请求。

## 修复与检查

后台元数据复用 `createRequestRecovery`，每次读取八秒超时、六次指数退避及抖动，共同一分钟期限。进行中的通知合并。切换页面/会话、前台详情读取及更新本地版本会取消旧读取，迟到响应不能替换新状态。取消对所有合并的调用者返回 `false`。成功同步后仍只触发一次远端恢复回调，不等待侧栏。

耗尽后保留最后已读内容，不把后台读取失败说成对话失败；定期通知不会再开启六次重试，而是在 30 秒冷却后做一次探测。正常读取成功解除冷却。本阶段不改提交和续聊写入逻辑。

新增恢复及取消检查在旧实现失败，原五项元数据检查通过。修复后共 14 项元数据检查通过，包括拒绝取消的挂起操作、耗尽/单次冷却探测、页面退出、前台读取替代、取消合并请求及过期响应。相关会话资源、草稿、运行序列、审核/询问、任务和恢复操作回归共 53 项 Node 检查通过，三个前端合约通过（模块闭包、模型空闲/排队路径、版本化会话写入）。

## 真实打包页面

夹具仍通过真实 HTTP/TCC、草稿、队列和模型事件运行，只在隔离源码加入有界 GET 故障。新增 `detail/hold` 延迟一次详情 12 秒；可选 `--trace-metadata` 只记录真正的后台 GET 和取消信号。

`metadata-trace.json` 中，12:10:35.830 开始的读取于 12:10:43.843 超时取消，12:10:44.421 再次读取并取得新版本。另一次于 12:11:00.843 开始的挂起读取，在切换会话时于 12:11:08.212 取消，早于八秒超时。旧响应随后返回时，新会话仍保持正确；返回原会话后草稿“切换会话保留原草稿”仍为一份。再次外部修改会话名称触发两次 503，12:12:09.271、12:12:09.885、12:12:10.950 三次后台读取后显示新标题，没有中途错误提示。

该实例实际完成三次模型请求，所有用户输入各提交一次，零最终模型错误，见 `native-metadata.json`；`continued.png` 展示恢复后续聊。arm 重置对应计数，因此结束快照的 `detail_held: 1` 不代表只有一次挂起注入；两次挂起的过程以时间记录为准。发送第一条消息是在超时重试恢复之后，不能据此宣称已经实测挂起期间的发送。

## 输入完整性仍待定位

上轮输入记录覆盖了原生 `textarea.value` 属性，可能影响浏览器工具的填充策略。这次改为被动输入/组合事件记录，在隔离副本的现有赋值语句之前记录恢复文本，保留原生 accessor；不对产品加入输入记录。

中文及英文输入、草稿往返、模型切换、侧栏六次读取耗尽后的输入、新任务详情两次失败恢复均未再出现重复。实际两次模型请求的输入各一份，分别派发到两个不同 `wire_model`，零最终错误，见 `input-passive-trace.json`、`native-input-passive.json`。这一复测并不能确定之前未记录时的偶发重复原因，也不能把真实输入法或所有输入路径标记为通过；没有猜测性去重补丁。

打开打印的 URL；通过 `/api/v1/qa-session-arm/detail/hold` 设置一次延迟，然后用真实版本化 PATCH 从另一客户端修改当前会话标题，触发后台读取。读取期间选择另一会话，返回后核对草稿。`detail/2` 可复测静默短暂失败恢复。输入记录含完整文本，只用于没有私人数据的测试 Home。创建打印的 stop 文件结束，最长十分钟。
