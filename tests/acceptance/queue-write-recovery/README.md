# 待发送队列写入的有界确认

基线 `94be497`。队列 POST、状态 PUT、清理 DELETE 原先没有截止时间。写入已经成功而响应卡住时，会长期占住发送步骤；回执丢失后的确认也缺乏统一的目标、状态和内容校验。

## 修改

将队列 HTTP 协议移入 `prompt-queue-transport.js`，保留原队列渲染与缓存版本保护。单次写入八秒截止；不自动重放 POST、PUT 或 DELETE。响应丢失或超时后只读确认，复用六次指数退避与抖动、共同一分钟上限，页面退出取消等待。

确认校验当前设备选择、服务运行代、精确消息 ID，以及目标状态。队列 POST 还校验文本、附件、优先级和模型/思考/权限快照；消息已交给运行时，只接受匹配 ID 的不可变运行回执。重置 pending 不能用已经接受的运行证明成功。已取得页面写入令牌时，确认响应必须属于同一令牌，不能采用重启后的服务响应。

明确的额度、权限和队列容量拒绝立即保留原错误，不进入网络确认。无法确定写入结果时保留不确定标记供既有提交控制器处理；不能因队列和回执都不存在就重放 POST，因为另一个窗口可能已删除该消息，服务目前没有取消墓碑能证明它从未接收。

## 检查

新增十二项确定性 Node 检查，覆盖拒绝 abort 的挂起传输、暂时读取失败、精确内容/回执、禁止盲目重放、状态确认、删除确认、明确拒绝、目标切换、退出与迟到响应，以及服务重启。对照旧实现两项通过、十项失败；修改后十二项通过。原读取版本保护检查调整为真实的 staged → pending 协议，避免模拟服务返回另一个消息 ID 的不可能响应。

相关队列读取、提交控制器、会话运行序列共 54 项 Node 检查通过，四项前端合约通过。实际服务的五个前端文件与隔离打包源码逐字节一致，见 `build.json`。

## 原生打包页面

`manual_run_admission_qa.py --scenario writes` 启动隔离的 Windows 打包程序，执行实际 HTTP/TCC、草稿、队列、运行与回环模型路径。故障代理先完成真实写入，再截断回执或延迟十二秒；WebSocket 不可用，走实际轮询。产品没有测试注入。

- `queue-post`：真实 201 后截断 POST 回执，随后两次队列 GET 返回 503，页面自动继续。
- `queue-promote`：pending PUT 的真实 200 响应延迟十二秒；既有提交确认路径也会并行检查保存状态，本次在约 5.7 秒后继续到 sending，不能把该记录说成八秒超时验证。
- `queue-sending`：sending PUT 的真实 200 响应延迟十二秒，约八秒后确认继续。第一次清理 DELETE 成功后截断响应，再让两次队列 GET 返回 503，页面仍自动完成，并能发送下一条。

`proof.json` 与 `checks.json` 记录四条输入各一次模型调用和运行接受，每条输入只有一个 POST、两个不同状态的 PUT 和一个 DELETE，没有任何写入重放，零最终模型错误；所有队列为空、草稿提交标记已清除。页面观察与截图显示正常回复和可用输入框，没有中途错误，浏览器警告/错误记录为空。永久拒绝、始终无法确认、页面退出与重启边界由确定性检查覆盖，没有把它们宣称为真实设备验收。

候选位于 `.build/conversation-acceptance/mdo-queue-write-recovery.exe`，匹配 xs `3232f7b8efb0`，哈希见 `build.json`。匹配宿主和构建回执保留在 `.build/conversation-acceptance/host-3232`，便于后续隔离验证。日常程序、手机和官网没有替换。

```powershell
python tests/manual_run_admission_qa.py --scenario writes --packed <上述候选> --directory <新的隔离目录>
```

依次访问打印代理地址的 `/__qa/arm/queue-post`、`/queue-promote`、`/queue-sending`，在对应会话中通过页面发送。第三个会话恢复后再发一条。创建打印的 stop 文件保存记录并退出；夹具最长十分钟。

本阶段不包含压力或高负载测试。长期任务仍进行中：中断恢复的取消传递、其他入口错误体验，以及上一阶段备份回归的偶发源目录差异仍需继续检查。
