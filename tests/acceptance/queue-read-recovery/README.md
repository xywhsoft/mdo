# 待发送队列读取的静默恢复

基线 `8f8b2e6`。会话载入、提交确认和队列回执原先直接 GET，没有超时或退避。一个短暂失败会立即进入会话/发送错误路径；挂起读取会长期占住该会话队列的进行中标记。

## 修改与检查

队列和回执读取复用有界恢复，每次八秒、六次指数退避与抖动，共同一分钟期限；相同会话的队列读取仍合并。只读重试，不重复队列 POST、状态 PUT 或删除。队列版本保护保留，晚到的旧读取不能覆盖先完成的队列变更。

读取成功前验证队列数组、数量、重复 ID、文本、状态、优先级和附件 ID。无效数据不能当作空队列覆盖已保存消息。只有明确的 `queue_receipt_not_found` 404 代表没有回执；路由不存在、权限失败、错配或无效回执仍是准确错误，不能误判为可以重新提交。匹配当前 ID 的 `starting` 回执仍等待后续确认。

八项新增 Node 检查在旧实现一项通过、七项失败。修改后八项全部通过，覆盖合并/短暂恢复、耗尽保留消息、拒绝取消的挂起传输、页面退出后迟到结果、版本保护、无效响应及精确回执。相关运行序列、后台恢复、提交控制、元数据、读取恢复和附件清理共 72 项通过。四项前端合约通过。备份恢复前端适配器改为返回实际服务的缺失回执代码，并完整模拟事件监听的清理。

## 真实打包页面

`manual_run_admission_qa.py --scenario queue` 通过原生打包程序的 HTTP/TCC、草稿、队列、运行和回环模型测试。代理只对真实读取注入故障，产品源码无 QA 修改；代理不支持 WebSocket，走实际轮询回退。

初次载入 `queue-read` 会话时两个队列 GET 返回 503，随后可正常发送并显示回复。另一个会话的一次队列读取延迟 12 秒；页面在两个会话间切换后，另一会话正常显示和发送，返回原会话也能发送。未记录这次切换与超时的精确间隔，不能据此宣称已验证在特定毫秒内切换。挂起读取的八秒截止、取消和迟到结果由确定性检查单独覆盖。

`proof.json` 记录三条精确输入各执行一次、零最终模型错误，所有队列为空、草稿提交标记已清除。`browser-observations.json` 和 `recovered.png` 显示正常回复与可用输入框，无中途错误；浏览器警告/错误记录为空。回执短暂失败的产品队列路径本阶段由单元检查覆盖，原生启动回执另见 `run-admission-recovery`。

候选 `.build/conversation-acceptance/mdo-queue-read-recovery.exe` 按基线新的 xs 锁定版本 `3232f7b8efb0` 重新编译匹配宿主。五个实际 HTTP 文件与隔离源码逐字节相同，见 `build.json`。没有替换日常程序、手机或官网。

```powershell
python tests/manual_run_admission_qa.py --scenario queue --packed <上述候选> --directory <新的隔离目录>
```

先访问打印代理地址的 `/__qa/arm/queue-read`，再打开第一个 URL 并通过页面发送。随后访问 `/__qa/arm/queue-hold`，点击该会话并切换到第三个会话，验证正常输入与发送；返回原会话继续。创建打印的 stop 文件保存记录并结束，夹具最长十分钟。

没有压力或高负载测试。队列写入本身仍需要检查超时、结果确认和错误体验。
