# 草稿写入和发送意图的有界确认

真实打包页面中，草稿 PUT 已被服务端保存，但成功响应的正文挂起时，发送会一直停在“正在保存发送意图”。本阶段的故障正文挂起三十五秒；旧版确实等待正文放行后才完成发送，并非宣称永久失败。隔离旧版的页面和服务证据见 `baseline-waiting.png`、`baseline-browser.json`、`baseline-proof.json`。另用 `461b66e` 的草稿存储代码复核八项针对性检查，全部失败，见 `baseline-node.log`。

## 行为

- 初次写入只尝试一次。单次请求及正文解析最多八秒，之后使用安静的指数退避读取确认结果；本轮写入和确认共用一分钟期限。
- 已保存的完整快照包括文本、附件、固定提交 ID、状态、模型设置及待创建任务。确认成功只承认这份不可变快照，下一条编辑单独保存，迟到回包不能清空新输入。
- 若读取仍显示原版本，才允许携带相同正文和原版本号重试 PUT。服务端草稿锁下的版本比较只接受一次；原请求恰在核对后保存也只会使重试得到 409，随后继续核对。`native-cas.json` 是实际打包服务两次相同版本写入的结果：200、409，版本只增加一次。
- 其他窗口已保存不同内容时保留原有冲突保护。切换目标或离开页面取消等待；页面仍保有内存且返回时先核对已有写入，不盲目创建新的提交。
- 一轮确认耗尽时保留输入和原快照，显示“暂时无法确认草稿保存结果”及准确原因，避免把未知结果说成保存失败。可恢复原因的后台核对逐步延长等待，最多十五秒；明确的访问或额度拒绝不安排自动重试，仍允许显式重试。重新连接时不会每三百毫秒重放不确定写入。
- 已保存的上一条发送意图仍可在下一条草稿超过保存上限时得到确认。超限的新输入继续保留，并按已有规则说明大小限制。
- 提交清单读取、状态改变、删除和未确认提交的补存也加上请求期限。状态/删除/补存只发一次变更，再按同一 ID 读取结果；补存失败先交回发送控制器核对队列及回执，不在该流程中途另发一条草稿错误。补存的先行读取最多八秒，随后的变更和确认另共用一分钟。

## 验证

`test_draft_write_recovery.mjs` 使用生产恢复器及虚拟时钟，覆盖挂起正文、请求未到达、原请求迟到、其他窗口修改、一轮耗尽后的继续核对、页面生命周期、提交清单挂起、状态及删除、目标改变、调用方取消、永久拒绝、确认时拒绝及超限后续编辑。相关回归总计 101 项通过；独立源码的四项前端合约通过。几处旧检查原本返回空正文或仅返回版本号，现按真实接口返回完整保存快照；退出/返回检查改用实际事件类型，未放松产品确认条件。

`manual_image_upload_deadline_qa.py --draft-write-fault` 启动独立打包实例和回环模型，第一次当前会话草稿写入成功后挂起正文三十五秒，并让两次确认 GET 返回 503。修复页面在约 9.547 秒读取确认，早于旧正文的 35.016 秒放行。记录器在输入和发送之前安装，从输入到首次回复，草稿状态未显示错误；证据见 `debug-observations.json`、`first-turn-transport.json`、`recovered.png`。

第一条发送等待时继续输入的中文草稿保持完整，随后普通刷新恢复相同草稿并获得焦点；第二轮也成功。两次实际模型请求的文本与两条用户输入逐字相符，零最终模型错误，草稿和队列最后为空，见 `reloaded-browser.json`、`continued.png`、`proof.json`。回环模型仅返回测试标记，没有调用线上模型或使用用户凭据。

六个实际 HTTP 返回的生产文件与独立源码相同，见 `source-parity.json`。构建基线是 `461b66e` 加本阶段生产改动，锁定 xs `3232f7b8`，候选 `.build/conversation-acceptance/draft-write-recovery-package/mdo.exe`；SHA-256 `dfc206327030edc16c1e6b89e7a111e986c266e481e299e33a81e31c460c2014`，4,461,316 字节。语言文件仅加入本阶段文案，根目录其他未提交修改未混入候选。

本阶段没有证明首次读取完成前关窗可以持久保存新输入，也没有解决此前真实输入法重复输入的原因。安卓真机、原生剪贴板/导出及备份源清单的间歇失败仍待后续验证；没有压力或高负载测试，没有更新日常程序、手机或官网。
