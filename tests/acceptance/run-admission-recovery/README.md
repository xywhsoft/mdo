# 发送前检查与启动响应丢失的静默恢复

基线 `91da9a7`。原来的发送前恢复检查只有一次 GET、没有超时；暂时断网会直接中断发送，一个挂起请求也会占住同会话运行序列。启动 POST 的响应丢失时，页面立即进入“结果未知”，即使服务已保存精确的队列回执。

## 本阶段修改

发送前检查复用有界恢复：每次八秒，六次指数退避及抖动，共同一分钟期限。检查必须匹配项目、会话与有效版本信息，失败不能解锁旧任务重试。后台检查合并进行中通知，短暂错误保留已读恢复信息；耗尽后遵循现有 30 秒冷却，用户主动操作可立即重试。恢复面板的显式刷新走主动路径。

同会话序列支持取消等待和挂起读取。取消中间等待者不允许后面的请求绕过尚未结束的前一个请求。客户端超时只能证明客户端停止等待，不能证明服务端的写入被撤销。

启动 POST 仍只发送一次。响应丢失或八秒超时后，仅以当前 `queue_item_id` 查询不可变回执，再读取回执绑定的运行；尚未产生的回执及短暂读取错误有界退避。初次提交和确认共用一分钟期限。不会按提示词、最新运行或其他会话猜测结果，也不会重复 POST。确认失败仍保留原错误及提交结果未知状态，避免误派发；额度不足等明确拒绝立即终止，不进入确认重试。

## 检查

旧代码新增检查出现发送前检查不重试、错误作用域响应被采用及挂起检查不释放等失败；旧序列的取消中间等待检查无法完成，已终止该轮专用测试进程。修改后相关 94 项 Node 检查全部通过，包括 18 项运行序列检查、6 项后台检查，以及恢复操作、元数据、消息替换、提交控制、读取恢复和恢复决策回归。四项前端合约通过：模块闭包、运行控制、空闲/排队模型路径和中断恢复。记录见 `unit-tests.txt`。

## 真实打包页面

使用隔离打包程序和真实 HTTP/TCC、草稿、队列、运行及模型事件。模型是回环测试服务，不涉及在线模型或用户密钥；代理只对真实响应注入故障，没有修改产品源码或伪造运行结果。WebSocket 在代理中不可用，实际轮询回退路径同时得到验证。

| 故障 | 实际注入和结果 |
| --- | --- |
| 发送前检查 | 队列保存后两个恢复 GET 返回 503；随后正常回复，启动 POST 一次 |
| 启动响应丢失 | 原生服务返回 202 后仅转发响应前四字节；两个回执 GET 返回 503，第三次取得回执；启动 POST 一次 |
| 启动响应超时 | 原生服务接受后将响应延迟 12 秒；页面八秒超时后读取一次回执确认，不重复 POST |
| 恢复后续聊 | 同会话直接发送另一条消息并正常完成 |

`proof.json` 记录四条精确输入各触发一次模型调用、四次实际启动、零最终模型错误。所有队列为空、草稿提交标记已清除，未残留结果未知状态。`browser-observations.json` 显示等待时保留待发送消息，最终显示正常回复且无中途错误提示；浏览器警告/错误记录为空。`continued.png` 展示超时恢复后继续对话。

干净候选为 `.build/conversation-acceptance/mdo-run-admission-recovery.exe`，锁定 xs `858a6ad1dde4` 宿主；五个实际 HTTP 前端文件与隔离源码逐字节一致，见 `build.json`。本阶段未包含工作区其他平台、工具包及更新功能的未提交修改。

```powershell
python tests/manual_run_admission_qa.py --packed <上述候选> --directory <新的隔离目录>
```

打开打印的代理 URL，依次选择三个会话。在终端访问 `http://127.0.0.1:<proxy_port>/__qa/arm/preflight`、`/lost` 或 `/slow`，随后在对应会话通过界面发送；每次 arm 新建一个计数阶段，不能为了读计数再次 arm。最后在慢响应会话发送普通续聊，创建打印的 stop 文件保存原生记录并结束测试。夹具最长十分钟，不执行压力或高负载测试。

本阶段没有替换日常 mdo.exe、手机或官网。待发送队列本身的读取/写入故障、偶发输入重复及真实系统输入与 Android 路径仍需继续核查，长期任务保持进行中。
