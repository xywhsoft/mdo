# Windows x64 预编译 .o 对照测试

结论：预编译适合减少启动时的编译工作。当前完整程序在已有 Home 下的 API 就绪中位数缩短约 **22.6%**，
但保留源码的成品增大约 **13.1%**。直接删源码能缩小包，却会破坏核心源码覆盖插件，不适合作为完整功能发布方案。
本轮增加测试工具和证据，没有切换默认构建方式或发布程序。

## 方法

- 同一台 Windows x64 机器、同一份 mdo 应用源码（`97a45cb4`）、同一个已构建精简 xs/xsw 宿主，版本保持 0.8.8。
- 宿主、TCC 和 SDK 均复用现有 `.build/host` 与锁定 SDK；没有创建工作树、复制 SDK 或启用其他 Agent。
- 对象由宿主内置 TCC 生成。预编译状态限制宿主符号注册，复制当前宿主的编译宏，避免把编译进程的 ASLR 地址写入对象。
  检查产物为 ELF64 x86-64 可重定位对象、使用 Windows x64 调用约定，没有带非零值的绝对符号。
- xs 原有 `tcc_add_file` 直接读取对象，不需要改 xs 加载器。通过 `xs.json` 的 `devfile` 选择 `.c` 或 `.o`。
- 编译器阶段每组 9 次；完整程序每个版本使用新 Home 3 次、已有 Home 9 次，共 48 次计时启动。
  版本顺序轮换，已有 Home 每次恢复同一份准备好的快照，恢复操作不计时。
- 启动边界为创建进程到首次 `/api/v1/bootstrap` 返回 `ready=true`。测试使用 1 个工作线程及 HTTP 服务模式，
  不打开 WebView，**不包含窗口创建、网页首屏渲染或模型首 token**。系统文件缓存未清空，因此不是 OS 冷缓存测试。
- 所有试验在项目 `.build` 下完成；未修改已安装程序、账号或用户会话，没有调用付费模型。

## 编译/加载阶段

以下不执行 mdo 的 `ServiceInit`，包括编译状态创建、源码编译或对象读取、重定位和状态释放。

| 方式 | 9 次中位数 |
|---|---:|
| 完整 C 源码编译并重定位 | 820.1 ms |
| 预编译对象读取并重定位 | 13.9 ms |
| 裁剪符号后的对象读取并重定位 | 14.2 ms |
| 构建时生成对象 | 771.1 ms |

这一阶段约减少 98.3%，但不能据此声称完整程序启动快 59 倍。
程序还需要读取/解压包、初始化 SDK、扫描扩展、初始化配置和存储。

## 完整程序与体积

MB 采用十进制；原始字节、SHA256、每次采样和范围见配套 JSON。

| 版本 | 成品大小 | 新 Home 启动中位数（3 次） | 已有 Home 启动中位数（9 次） |
|---|---:|---:|---:|
| 当前源码加载 | 6.862 MB | 2.588 s | 1.674 s |
| 预编译对象，保留全部源码 | 7.762 MB | 2.311 s | 1.296 s |
| 对象裁剪符号，保留全部源码 | 7.752 MB | 2.584 s | 1.324 s |
| 对象裁剪符号并移除业务源码/头文件 | 6.543 MB | 1.968 s | 1.326 s |

原始对象 7,138,568 字节，裁剪后 7,137,456 字节；压缩后的成品只减少 10,209 字节。
裁剪使用 `strip --strip-unneeded`，显式保留 `ServiceInit`、`ServiceUnit`、`ServiceSwap`、`RequestProc`，
保留重定位和 Windows unwind 数据。此步骤没有显示可靠的启动收益。

新 Home 样本较少且包含文件创建，波动较大。已有 Home 的源码版范围为 1.464—1.828 秒，
保留源码的预编译版为 1.161—1.479 秒。本轮数据适合评估方向，不应外推为所有机器的固定收益。

## 插件与基础功能

每个版本均通过首页、前端模块、模型目录、Application SDK 目录和原生 Markdown 解析检查。
另外按当前目录扩展格式，各做一次真实原生 C 插件加载和一次核心源码覆盖，共 8 个用例：

| 版本 | 原生 C 插件注册工具 | 核心覆盖修改 bootstrap 版本 |
|---|---|---|
| 源码版 | 通过 | 通过 |
| 预编译，保留源码 | 通过 | 通过 |
| 裁剪对象符号，保留源码 | 通过 | 通过 |
| 移除业务源码/头文件 | 通过 | **未生效，进入恢复模式** |

核心覆盖流程仍需从 `/app/generated/mdo_unity.c` 编译经过验证的覆盖视图。
对象不能代替这份可编辑源码。启用核心覆盖插件时，预编译基础服务之后仍会发生一次源码编译。
没有对整个应用的所有功能做发布级回归，也没有对原生 WebView 首屏进行计时。

## 完整构建耗时

同样使用缓存宿主，保留依赖校验、源码生成、临时打包树、Windows CLI 转发器和一次最终打包。
对象版在打包前增加预编译，而非先做源码包再二次打包。交替执行 3 对：

| 构建流程 | 中位数 |
|---|---:|
| 当前源码包 | 11.277 s |
| 预编译对象包，保留源码 | 14.535 s |

预编译版多约 3.26 秒（28.9%）：生成对象的独立子进程约 0.84—0.89 秒，
新增对象使压缩打包从约 2.0 秒增加到约 4.4 秒。三次源码构建、三次对象构建各自的 EXE SHA256 完全一致。
最终额外重建源码基线，其字节和最初计时的源码包一致。

## 建议

1. 启动优化采用 `.o` 作为正常入口，保留 C 源码、生成的头文件与模块 SDK，维持现有扩展能力。
2. 开发模式继续使用 C 入口。正式切换前增加对象缓存指纹：完整源码/生成文件、TCC/宿主/SDK 版本、平台架构及编译宏/选项。
   指纹变化时重新预编译；不能只根据 `.o` 是否存在复用，也不能把本次 Windows 对象直接用于 Linux/macOS/Android。
3. 体积优化单独评估压缩、重复资源和更强编译器生成的兼容对象。本次仅测试锁定 TCC 产生的对象，没有测试 GCC/Clang 优化对象，
   也没有证明可在保持完整功能时同时缩小当前包。不建议仅为约 4.7% 的体积收益移除源码。
