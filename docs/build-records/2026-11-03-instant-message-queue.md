# 首条消息即时展示与队列续发

## 行为

- 点击发送即显示用户消息及对应回复占位，不等待 Home 草稿保存、会话创建或运行初始化完成。
- 使用同一个提交 ID 贯穿界面、Home 草稿、队列收据和会话事件。正式事件到达时替换占位，不能按文本猜测或再次发送。
- 提交失败在对应回复处显示原有受保护的重试入口；刷新后仍从持久化草稿恢复消息。确定拒绝后重试可重新绑定会话 ID。
- 普通回复失败后继续下一条；主动停止保留并暂停后续消息。鉴权、配置和提交结果不明等入场问题继续使用原有保守确认机制。
- 原生队列工作线程正常进入 sending/claimed/prepared 状态时，不再误报“首条消息可能已被服务端接收”。

## 确认的问题

1. 原界面等待持久化和会话创建才有消息展示，准备期间反馈不足。
2. 队列界面只将浏览器 busy 标志当作发送所有者，遗漏原生 managed 工作线程，正常提交被误判为结果不明。
3. 原生队列将所有非成功终态均当作暂停原因，普通模型错误也会阻止下一条。
4. 当前运行中首次入队时清空前序运行 ID，运行恰好结束或被停止时可能丢失关联。现在入队前记录活动运行，且不持有队列锁读取运行快照。
5. 提交 ID 已存在于持久化会话事件中，但事件 API 未返回它；现补充返回，供界面准确消除临时气泡。

运行管理器原本已有后台收尾线程；本次没有增加重复的运行泵。

## 验证

- Node：80 项通过，涵盖即时占位、重试重绑定、错误控件焦点、原生发送状态、草稿/队列请求截止与收据恢复、图片及停止控制。
- 实际 Windows EXE + 本地模型桩：HTTP 400 后下一条自动完成；立即入队后停止时后续保留；提交 ID 返回；无重复模型请求。
- 实际 EXE：运行中中断、重启后恢复队列、重复启动不重放、显式恢复及后续消息完成。
- 实际 EXE：排序、冲突、幂等、提取、插队、无界面续发、停止/恢复和重启矩阵通过。原源码测试的通用探针因 workspace_state 写入钩子变化无法启动，因此复用同一矩阵，替换启动适配器直接测试打包程序。
- 浏览器：故意阻塞会话创建时，消息已显示；正式事件到达后只有一条用户消息；运行中追加消息即时可见；两条依次完成；配置失败在回复内展示；刷新和明确重试不丢消息、不重复气泡；390×844 无横向溢出；无浏览器错误日志。
- 所有模型验证均为有界的本地桩，不调用真实供应商，不使用用户账号或凭据。
