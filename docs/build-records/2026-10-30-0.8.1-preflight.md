## 尚未解决的问题

### 1. 清理回滚存在间歇失败，不能按测试过期处理

`test_home_purge_runtime.py` 两次整套执行分别在 `fail-9` 和 `fail-11` 的合成故障中出现：

```text
purge_end=0 committed=0 frozen=1 reserved=1
purge_write_blocked=1
```

预期是未提交并完成回滚、解除冻结。实际进入保留日志及阻止继续写入的恢复保护。正常提交路径和持久清理收据检查已通过，仍不能据此排除异常回滚问题。

3 次独立 `fail-9` 定点复现、随后 20 次 `fail-9`/`fail-11` 定点复现均通过，逐文件核对没有增删或字节变化。之后增加仅限夹具的恢复阶段/错误链记录，并改为失败时保留现场，第三次整套执行通过，未捕获新的失败事务。这不能覆盖或取消前两次整套失败。前两次失败的整套测试会清理临时目录，尚未拿到原始失败事务日志及底层错误链，不能声称已定位根因、已经修复，或证明失败事务的数据恢复完成。

下一步应先让整套故障用例保留失败现场并记录底层错误链，再区分文件访问冲突、身份校验和回滚逻辑；应继续保持失败时的冻结保护。

### 2. 模型取消的错误分类间歇不一致

最终模型相关复验中，SDK 流终止探针的取消场景曾返回：

```text
call0=result:-1 code:network ms:164
call1=result:0 code:none ms:14
```

该测试在约 150 ms 主动取消，期望取消分类；第一轮该场景和之后 3 次单场景重试均通过。它直接调用 SDK，不经过本轮被其他任务修改的模型请求适配函数，因此不能只归因于那几份应用源码的并行变化。尚需捕获取消标记、底层错误及完成时序，确认是否存在取消/连接关闭竞争；未改产品代码掩盖该异常。

### 3. 发布探针与现行目录、鉴权、SDK 合同脱节

失败中已确认存在多种过期前提：

- 引用已删除的 `default-home/modules/agents/builtin_default.c`、旧整体工具包目录。
- 使用旧平铺命令、插件/模块 SDK 服务或未提供扩展 manifest/revision 的保存接口。
- 使用默认在线模型创建会话，却未建立本地测试登录或显式配置本地模拟模型。
- 仍断言启动后 Home/agents 目录完全不存在，而当前内置扩展身份安装会创建这些目录。
- 手工裁剪 C 源码的探针未链接新的扩展目录/运行期服务，出现未定义符号。

全部失败测试的名称、退出码与日志摘要位置保存在配套收据和私有日志；尚有未归因断言，不将 71 项一概判定为测试问题。应更新夹具并逐项重跑，保留失败断言，不靠跳过用例或放松产品安全规则取得绿色门禁。
