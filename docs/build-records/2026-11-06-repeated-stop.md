# 连续发送、停止后编辑入口丢失

版本保持 0.9.3。本轮没有发布上线，没有替换用户正在运行的程序。

## 原因与修复

本机只读检查发现，目标消息的取消收据已经为终态，服务也没有活动运行；页面仍显示“正在停止”。编辑入口依赖会话运行状态，因此被一并隐藏。

1. 前端曾记住一个运行，但最新运行列表不再包含它时，原逻辑既不确认该 ID 是否还存在，也不清理 `activeRun`。健康的实时连接还会关闭兜底轮询，导致这段状态一直保留。现在仅在完整列表缺少当前 ID 时，额外请求该运行的精确读取端点；只有 `404 + run_not_found` 才清理。网络错误、权限错误和其他模糊失败不会被当成停止成功。
2. 原取消状态匹配条件允许“没有运行 ID，但会话相同”。准备前停止的旧消息因此可能污染同会话的新运行。现在必须同时匹配项目、会话和非空运行 ID；匹配的终态取消收据可以结束对应运行的前端状态。
3. 已经精确确认不存在的运行，在同一个服务代际中不再被迟到的旧列表恢复。记录仅是有界的运行状态，切换设备/服务代际后清空，不新增诊断日志。

编辑仍采用普通图标及行内编辑器，停止仍只通过输入框按钮，没有增加特殊操作入口或放宽停止完成前的编辑条件。

## 验证

- 相关前端回归 **386/386**；版本编码回归 **5/5**；前端模块图 **271** 个模块连通。
- 普通原生执行：发送、停止、以相同文字编辑重发、再停止，再发送、停止；三次循环后对应编辑入口均可用，刷新后正常，模型回调恰好三次。
- 原生准备阶段：连续相同文字重发、停止；编辑入口每次恢复，没有实际模型调用。
- 原生服务配合浏览器故障注入：第一遍停止后编辑重发，第二遍让一个已被前端观察到的运行从列表消失，并让精确读取返回不存在。旧代码稳定超时并保持停止中；修复后会确认并清理该 ID，恢复编辑。随后再次注入旧列表，不会复活失效运行。
- 同时覆盖无运行 ID、旧运行 ID、不同会话以及畸形取消标志，均不能影响新运行。

全部模型调用为离线测试回调，没有使用用户的模型账号、密钥或计费接口。本轮没有 Android 真机测试。
