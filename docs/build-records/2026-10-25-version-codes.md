# 十六进制版本码迁移（2026-10-25）

客户端提交 `1edae54e`；平台仓库提交 `a810d09b`，均在 master。规则见 [version-codes.md](../version-codes.md)。本轮未修改线上目录或更新目录，未正式发布。

## 已完成

- `version_code` 作为八位十六进制字符串，与历史十进制 `build_id` 分开。客户端、缓存、平台选择和后台列表统一忽略最高字节后比较；同版本用安装编号识别重新打包。
- `0.6.0` 新规则基线为 `60000000`；官方后续 1.0 之前使用 `60` 前缀，1.0 从 `00010000` 清除前缀。读取也接受提前清除前缀的 `00000601`。
- 安装编号继续递增，本轮八种产物从 `60000001`～`60000008` 推进为 `60000009`～`60000016`。Android APK 的系统版本编号保留安装序列，不随语义前缀清零。
- 发布脚本检查新版本码、构建汇总、APK 资源元数据及打包宏一致，后台新上传要求填写文件版本码；同一安装编号不能更换版本身份。历史无新字段记录仍兼容。
- 按用户要求新增长期记忆更新记录，不含凭据、会话、生产账号信息。

## 已通过验证

- 5 项版本码测试：uint32 最大值、256 种最高字节、大小写与点分字节、畸形输入、官方前缀与 1.0 阈值；C 编解码器使用 GCC 严格警告编译运行，与平台头文件逐字节比对。
- 4 项 Android 资源打包测试，保留原安装编号并记录新版本码；生成脚本、Android 分版安装编号和发布记录校验的针对性契约通过。
- `test_update_runtime.py` 真实 xs/TCC/HTTP 测试通过：`60000000 → 00000601`、1.0、同版本重新打包、Android 安装序列保护、无字段旧清单、畸形清单拒绝、校验失败、取消、强制更新缓存离线恢复与撤销。
- 平台 `test_mdo_version_codes.py` 的隔离服务测试通过：新旧请求排序不同但均符合各自协议；`6000FFFF → 00010000`、同版本重包、禁止复用安装编号更改版本码、畸形及空字节参数、后台版本编辑脚本。
- 平台 Node 编解码与排序测试通过；客户端 232 个前端模块可解析、可达。
- Windows GUI 成品从空目录运行，知识库原生 CRUD、路径检查、文档读取和卸载回归通过。没有调用真实模型。
