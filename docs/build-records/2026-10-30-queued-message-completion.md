# 对话结束后队列迟迟不发送（2026-10-30）

修复两处可复现的延迟：原生模型通道收到有效 SSE 结束事件后仍等待 HTTP 收尾，以及前端一次慢资源读取阻塞后续运行状态、队列刷新。版本保持 0.8.0；本次没有发布官网或自动更新，也没有替换用户正在运行的程序。

## 产品修改

- SDK 的 HTTP 泵在协议已结束、尚无完整 HTTP 收尾时结束模型调用，丢弃未排空连接。已经完整收尾的连接仍可复用；不把最后一段文字或单独的 `finish_reason` 当成提前结束依据。原始响应体转换钩子仍保留完整响应体语义。
- 保留 Chat `[DONE]` 前的延迟用量、Responses 终止事件用量及 Anthropic `message_stop` 前的用量；同时补齐原先未读取的 Responses `response.incomplete` 用量。
- 实时资源刷新分别合并请求，每个资源最多一个在途刷新，慢任务、恢复检查不会阻塞下一次运行及队列读取。
- 存在运行或待发送消息时，即使实时连接正常，也每 2.5 秒触发运行与队列核对。纯空闲实时页面不增加轮询；页面隐藏时暂停。
- 收到当前主 Agent 的完成事件、后端尚未释放运行时，显示“正在结束上一轮”及相应队列提示。仍由后端结束状态决定下一轮准入；子 Agent、旧运行 ID 和其他会话的完成事件不能提前放行。

## 验证

相同本地合成服务先发送完整回答、用量和 `[DONE]`，仅将 HTTP 最后一个块延迟 4 秒：修复前最新候选程序约 4156ms 才发出下一条；修复后正式回归为 391ms。此为回环夹具测量，不代表实际供应商响应延迟。

- 原生协议回归通过 12 种场景：三个协议结束、Responses 截断结束、供应商失败、Anthropic 错误、无结束标记的截断、畸形 SSE、延迟用量、取消、正常连接复用、TLS 收尾延迟。未排空连接未被下一次调用复用；完整连接复用已核对。TLS 延迟收尾场景约 1042ms 完成，包含既有关闭等待。
- 打包程序的队列发送、排序、冲突、幂等、提取、引导、无页面排空、停止/恢复及重启通过；原有 TLS 代理回归通过。
- 全量前端在当时的 1225 项测试中通过 1223 项、原有跳过 2 项；随后新增实际应用接线回归，最终相关定向 30 项全部通过。239 个模块可解析并可达，SDK 构建契约 2 项通过。
- Windows 原生宿主和程序重新编译，依赖补丁及回执匹配。Android ARM64 原生库与独立测试包重新编译，通过签名、对齐检查，并核对 APK 内原生库字节与构建结果一致。

额外尝试的旧 `test_run_completion_runtime.py` 未能启动：它引用已删除的 `default-home/modules/agents/builtin_default.c`。没有将它计为通过，也未扩大本次修改去调整旧夹具；结束后立即准入下一轮的实际路径由打包程序队列回归覆盖。未进行界面视觉或 Android 真机验收。

全部模型请求使用本地合成服务。用户账号、会话和真实安装未修改；原有扩展依赖工作区改动保留且未混入提交。
