# 移动网络直连深入排查（2026-10-19）

本轮确认了移动网络的端口依赖映射，以及 mdo 将控制端与底层握手发起端绑定的实现限制。后者已经通过实际 APK 与公网 Linux 的方向反转对照复现。反转方向仍不能让本次两个独立 NAT 直连，不能将这一场景宣布为已修复。

可提交的脱敏收据为 `tests/acceptance/xrudp-mobile-nat/diagnosis.json`。本轮没有修改产品实现；只在独立副本中加入计数、第二 STUN 探测和固定反向握手实验。未发布或替换线上服务。

## 验证对象与隔离

- 应用来自已提交的 mdo `e6865f3c4fe889b12cad3db26a3555b32a2e4bd0`，SDK `a6906e202e051b6bc624f16ec131b88892963457`，XRUDP 运行时 `3d55ec41e13f0884ffe840d44a57a0189d9310f3`。
- 真机为 Android 16 ARM64。使用独立 QA 包和独立 Home，未读取或修改日常 mdo 的 Home。
- 所有实验 APK 使用相同原生库，SHA-256 `559cbb723b9b5d4cdf273eef21302358c6aed1bfcd913ea63903f127e4cce11d`。实际 APK 的 JNI/TCC 路径执行探测，已不只是 shell UID 的旁路测试。
- 手机默认网络核验为 CELLULAR，电脑使用原有网络。ADB/SSH 只承载本机测试账号信令与控制；业务与握手 UDP 经过设备网络。
- 公网对照使用服务器上既有 SDK 宿主，在独立目录、独立 Home 和回环 HTTP 控制端口运行，不修改线上账号、会话、计费、服务进程或配置。

## 同一连接套接字的映射证据

在原始连接的同一 `xrudpendpoint`、同一 UDP 套接字完成主 STUN 后，向相同公网 IP 的另一个端口做一次发现。原始对外候选、密钥、绑定和协议不变。

两个控制方向的结果一致：

| 设备 | 目标端口变化后的公网映射 |
| --- | --- |
| Windows | IP、端口均不变 |
| 手机 APK | IP 相同、端口不同 |

因此，STUN 获得的手机端口不能直接视为手机访问任意对端时的公网端口。该结论只描述已测到的目标端口依赖行为，未声称完整刻画运营商的所有 NAT 与过滤策略。

两端仅收到两个 STUN 回复，未完成握手；无效包、地址拒绝、速率拒绝、容量拒绝和 IO 错误计数均为零。临时第二 STUN 服务仅响应四个匹配请求，随后退出并关闭套接字，没有记录事务内容、令牌或密钥。

## 公网方向反转对照

`rendezvous.inc.c` 中，`S->Initiator=!Config->Listen` 同时决定信令角色和底层握手角色；只有该发起端调用 `MdoRudpDialCandidates`。被控制设备只能监听。这会漏掉“被控制设备主动连接可达控制端”这一可用方向。

实验仅在隔离副本中反转原生 `Listen` 与 Dial 条件。UI 控制端、信令角色、控制端选路、固定公钥、应用上下文、只读权限、一次性 offer 和 RPC 方向均保持原样。

| 场景 | 实际底层发起者 | 结果 |
| --- | --- | --- |
| 原实现：手机控制公网 Linux | 手机 | 422 ms 完成握手，完整业务通过 |
| 原实现：公网 Linux 控制手机 | Linux | 约 9 秒后失败 |
| 反转实验：手机控制公网 Linux | Linux | 失败 |
| 反转实验：公网 Linux 控制手机 | 手机 | 453 ms 完成握手，完整业务通过 |

两项成功均验证目标端恰好写入一次、实时订阅、独立只读连接、取消后的中继收据查询、注销，以及关闭后两端原生传输数归零。结果证明移动 UDP 和原生握手本身可用，也证明不能简单将全局发起方向调换。

原实现的失败公网端点在一次主 STUN 发现后累计收到六包，协议拒绝计数为零、没有确认连接；多出的五包与手机发出的五次 punch indication 相符。该判断来自计数和代码路径，未逐包抓取。源码确认当前 punch 为未认证的 STUN indication；运行时没有向应用提供经过认证的 peer-reflexive 候选。不得直接相信任意 UDP 包的来源并解除握手地址校验。

早期公网原始日志按追加方式收集，第二项含上一项日志；脱敏收据按本次唯一公网本地端口过滤。后续方向反转驱动在每次运行前记录日志偏移，结束时还通过精确配置路径和宿主路径校验远端测试进程退出，避免将 SSH 子进程退出误认成原生进程退出。

## 两个独立 NAT 的剩余边界

原方向两项失败；固定反向实验也两项失败。后者的两个端点只收到主 STUN 回复，未收到对端握手，且协议拒绝与 IO 错误计数为零。握手方向修复有必要，但不足以独立解决这对网络。

电脑当前以太网类别为 Private。`netsh advfirewall` 的只读查询确认，测试宿主已有启用的 Private UDP 入站允许规则；Public 的阻止规则不能据此当作当前有效阻断。PowerShell 防火墙管理接口拒绝访问，临时规则创建失败，没有改动系统规则。未执行管理员抓包对照，因此仍不能确证包具体被哪一级 NAT、运营商或主机过滤组件丢弃。电脑没有可用的全局 IPv6 地址，本次没有可选的公网 IPv6 直连路径。

## 产品修复方案

1. 将信令控制角色与原生握手角色分离。在固定总超时内协商或竞争两种握手方向，由控制端选择一条已完成认证的路径；失败或落选的工作全部取消。不能只固定换成由被控制端发起。
2. 为需要学习实际对端来源的场景增加认证连通性检查。探测绑定本次会话、双方公钥、一次性随机量和路径编号；验证后才纳入有界候选，再完成原有公钥固定的握手。不能把未认证 STUN 来源作为可信身份，也不能放开未完成握手的地址校验。
3. 控制与只读权限不随网络发起方向变化；不同方向或轮次的迟到消息不能重新选路或延长总时限。业务只在最终选定路径后准入，防止连接竞争导致写入重复。
4. 加入可重复的端口依赖映射、端口过滤、方向不对称、重复/过期选路与取消回归；再用本次真机两网络复验。双方策略确实不允许穿透时，继续使用已有中继兜底。

这些是待实施的产品修复，固定反向实验不能作为自动协商已完成的证据，也不能替代双 NAT 正向直连或 72 小时验收。
