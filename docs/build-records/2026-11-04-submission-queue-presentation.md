# 聊天消息与待发送列表互斥显示

问题：发送按钮已将本地提交投影到聊天区，底层草稿、队列和启动收据仍在完成握手。原来两个组件各自渲染同一份消息，准备回复期间会出现一份聊天消息和一份“待发送”副本，首条消息也受影响。这是显示归属问题，不代表消息已被模型处理或实际重复发送。

改动：

- 聊天组件按提交 ID 提供当前显示归属。待发送组件只隐藏已在聊天中显示的消息，不移除、确认或重发任何持久化队列记录，待发送数量仅统计实际显示的排队项。
- 空闲时当前首条提交立即进入聊天；后续消息保留于可编辑的待发送列表，到轮次或服务端已认领时移入聊天。已经进入聊天的消息在准备、失败和回复丢失期间保留原位置。
- 历史中的根 Agent 启动记录同样提供归属证明，防止队列轮询较慢时重新展示已进入历史的消息。按 ID 匹配，相同文本的不同消息仍然独立；会话、项目和设备切换不会沿用旧显示归属。
- 失败的本地提交仍在聊天中显示错误及原有恢复控件。服务端队列暂停或需要确认时保留继续、移除等操作，但不再次复制消息正文；真正等待的后续消息保留排序、引导、撤回等功能。其他客户端撤回的排队项不会被补画为已发送消息。
- 等待区提示描述剩余排队项，正在聊天区准备回复的队首不再让后续排队项误显示为“正在发送”。

本轮仅修改前端显示和接线，没有改动发送协议、确认规则或模型请求；没有修改版本号、构建安装包、官网或自动更新。线上仍是此前发布的 0.9.1，根目录八种正式产物及发布记录保留。

验证：72 项相关队列、提交、新会话和恢复回归通过；最后补充的定向检查共 16 项通过。真实 Chromium 的桌面/窄屏共 10 组队列行为场景通过，包含排序、撤回、焦点和滚动保留；最终显示范式又在 1280px、360px 验证首条、创建迁移、历史接管、轮次转移、暂停恢复、数量和提示、移除及按钮边界，全部通过。前端模块图 263 个模块解析并连通。
