# 公共库预编译：复制目录流水线实测

状态：**已放弃，仅保留历史评估记录**。2026-11-04，用户决定停止整个 `.o` 预编译路线。实验脚本、测试和相关临时产物已清理，默认构建保持源码加载。历史工具可从提交 `a64d7aa8` 查阅，下文命令仅用于说明当时的测试过程。

结论：本轮审查过的公共库可以在复制后的 app 中编译成 `.o`，移除实现源码后仍可启动并使用所测插件；但成品仅减少 **13,428 字节（0.196%）**，没有测出可靠的启动速度收益。暂不建议据此切换默认构建。

这是公共库拆分实验，与同日的完整核心预编译实验不同。当前测试应用版本为 **0.9.0 / 05000900**；没有发布产物。

## 范围与实现

- 输入清单：`docs/precompile-candidates.json` 的第一批 7 组、15 个文件，共 135,434 字节。
- 组别：基础校验/路径、ZIP、扩展元数据/依赖图、提示文件解析、扩展格式、API 值辅助、平台电源辅助。
- Python 先复制 `app` 和项目公共 `include`，所有生成器、头文件提取、对象生成、源码移除和打包都发生在 `.build/partial-precompile-20261104/project`。
- 提取 89 个头文件函数，保留声明、类型和宏；只移动私有 Unicode 表，小型公共类型数组仍保留。两份独立实现 `src/api/value.c`、`src/power/inhibitor.c` 从复制树移除。
- 重建复制树里的 Application SDK 镜像和原生函数绑定，移除临时提取的实现源文件。7 个 `.o` 合计 199,442 字节。
- 对象使用锁定宿主的 TCC、编译宏和 SDK，限制宿主地址注册。产物为 ELF64 x86-64 可重定位对象，使用 Windows x64 ABI，没有带非零值的绝对符号。
- 原始 `app`（含 generated）和公共 `include` 的全树哈希在构建前后以及最终复核时一致。没有复制原生 SDK、创建工作树、修改安装目录或读取模型凭据。

测试三种入口：

1. `source`：复制 app 后正常生成并打包，启动时编译源码。
2. `partial`：入口创建第二层 TCC 状态，加载公共对象并编译业务源码；用于观察适配层成本。
3. `partial-direct`：业务入口以 `#pragma comment(lib, ":name.o")` 直接链接对象，配置 `dev_lib`，去掉第二层加载器。使用 xs 现有能力，没有修改 xs 原生宿主。

两种对象版均在复制树中适配业务核心覆盖的编译路径，使重新编译时能链接相同对象。该适配不是对原始 app 的改动。

## 体积

同一个原生宿主、同一套应用资源，比较最终可执行程序实际字节数。MB 采用十进制。

| 版本 | 字节 | 成品 MB | 相比源码版减少 |
|---|---:|---:|---:|
| 源码版 | 6,863,236 | 6.863236 | — |
| 公共库对象，二层加载 | 6,850,566 | 6.850566 | 12,670 字节 / 0.185% |
| 公共库对象，直接链接 | 6,849,808 | 6.849808 | 13,428 字节 / 0.196% |

删除源码不等于能从压缩包中减去同样大小：包中增加了对象、声明和绑定，原有源码本身也会被压缩。这里直接比较最终成品，已经计入这些成本。

## 加载与启动速度

环境：Windows 10 x64（19045），AMD Ryzen 5 5600，Python 3.12.10；复用锁定 SDK 与已有 xs/xsw 宿主。单进程顺序执行，各版本轮换顺序，没有并行测试进程。

启动边界为 `Popen` 到 `/api/v1/bootstrap` 首次返回 `ready=true`。HTTP 服务模式、1 个工作线程，**不包括 WebView 窗口、网页首屏或模型首 token**。未清空系统文件缓存，所以“新 Home”也不是 OS 冷缓存测试。已有 Home 每次从同一快照恢复，恢复操作不计时。

最终三版本共 **54 次计时启动**：每版新 Home 3 次、已有 Home 15 次；另有准备快照的启动不计入。CPU 时间为进程 user + kernel，Windows 计时有量化粒度。

| 版本 | 已有 Home 就绪中位数（15 次） | 相比源码版 | 进程 CPU 中位数 | 新 Home 就绪中位数（3 次） |
|---|---:|---:|---:|---:|
| 源码版 | 1,610.0 ms | — | 1,593.8 ms | 2,431.7 ms |
| 二层加载 | 1,721.9 ms | 慢 6.95% | 1,703.1 ms | 2,494.4 ms |
| 直接链接 | 1,678.6 ms | 慢 4.26% | 1,640.6 ms | 2,780.7 ms |

观测中位数没有显示加速，但样本波动较大，不能把这些百分比当成固定退化幅度。进一步按相邻轮次配对，计算“对象版减源码版”的时间差：

| 版本 | 配对差值中位数 | 中位数的 bootstrap 95% 区间 |
|---|---:|---:|
| 二层加载 | +135.3 ms | -72.2 ～ +238.2 ms |
| 直接链接 | +35.0 ms | -122.0 ～ +370.3 ms |

负数表示更快。区间均跨过零，**没有证据表明这一批公共库能带来稳定加速**。区间为描述性估计：固定随机种子 20261104，对 15 个配对差值做 10,000 次有放回重采样；没有控制后台负载、CPU 频率或机器间差异。

单独的“创建 TCC、编译/读取对象、重定位、销毁”探针也没有显著差距，每版 9 次：源码 948.4 ms、公共对象组合 925.6 ms、直接链接 959.4 ms。此探针不运行应用初始化，且三组依次测量，作为辅助观察，不能代替上面的完整启动测试。

本轮范围较小；较重的 xrt、xllm、xwork、md4c 等库本来就已在原生宿主内。结合结果推断，仅拆出这些辅助函数，不足以明显降低剩余业务源码、SDK 声明及初始化成本；声明/绑定、对象链接和适配层也有成本。没有对各成本做完整剖析，因此不将此推断作为精确归因。

## 功能与插件验证

- 三个版本均通过首页、前端入口脚本、模型目录、工具目录、Application SDK 服务目录及原生 `markdown.parse`（md4c）检查。
- 三个版本各做一次真实原生 C 插件加载和一次核心业务源码覆盖，共 **6 个用例全部通过**，均未进入恢复模式。
- 原生插件实际通过 SDK 调用 `MdoHttpUrlValid` 和 `MdoPromptParse`，然后注册可见工具，验证拆出的函数确实可调用。
- 核心覆盖替换 `src/api/resources.c`，API 返回版本 `precompiled-core-qa`，验证覆盖实际生效。
- 提取器 3 个单元测试通过：C 字符串/注释/局部表的边界、私有表与公共类型保留、异常后原始生成器路径恢复。

兼容性范围是“原生插件和保留源码的业务覆盖”。**已经移除实现的公共库本身不能再被源码覆盖直接修改**；改其实现或相关 ABI 需重新生成对象，或保留源码回退。未覆盖所有插件组合、所有应用功能或其他操作系统，不能视为发布级验收。
