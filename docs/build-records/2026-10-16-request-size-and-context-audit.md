## 本次故障

最后一次成功调用报告输入 255,622、输出 498 token，合计 256,120；模型声明上下文为 1,000,000 token。本次失败不是模型上下文耗尽。历史三次失败均为 HTTP 413，网关在转发之前拒绝。

用已发布 0.1.1 所锁定的原生 GLM serializer、会话快照和 18 个标准工具离线重建，请求为 1,050,076 字节，比网关 1 MiB 上限多 1,500 字节。前一调用的重建正文为 1,045,971 字节。没有录制历史线上请求原文；额外元数据可能增加字节，不能把重建大小当作抓包结果。分析未发送小说到模型，未修改原会话或项目文件。

Token 与 HTTP UTF-8 JSON 字节是两种不同的限制。此处应修正过小的传输限额，不应为迁就 1 MiB 而在约 26% 上下文时主动压缩。

## 旧版客户端实现与用户约定的偏差（已复现并修复）

1. `app/web/js/features/chat/token-meter.js` 的圆环只使用最后一次调用的输入 token / 上次模型上下文窗口。上次输出、本次输入估算未加入圆环；本次估算只单独显示。
2. 锁定的 `xllm-session` 将最后一次 usage 的输入与输出相加保存为 `uFillExact`，这一部分正确。但随后使用配置字节上限 / 4 加 256 的固定 `uIncrementMax`，没有累计实际新增消息。用户消息没有字节上限时，其增长预留为零。
3. 持久化只保存 `fill_seen`，没有保存精确 usage 及其对应消息位置；恢复后精确基准无效，见过 usage 的会话在下一次真实回包前被设为无压力。这会漏掉恢复后首个请求的预先压缩判断。

使用发布版原生宿主和隔离会话复现，未调用模型：

```text
上下文 100000；输入预算 87000；压缩阈值 82649
上次服务端输入+输出 61000；固定增量 16640
追加文本估算 30000 token 后：固定增量仍为 16640，压力仍为 PRUNE
61000+30000 已超过输入预算，但没有进入 COMPACT/OVERFLOW
保存并重载后：精确用量 valid=false，pressure=NONE
```

原始私有收据：`.build/novel-size-20261016/governance.log`。这些缺陷是独立风险，不是本次 413 的直接触发原因。

客户端修复应使用同一份上下文状态驱动显示和压缩：最近一次有效主调用的服务端输入与输出为锚点，累计锚点之后新增消息/工具结果/系统提示变化的估算；每次模型请求之前检查阈值，并保留输出空间和安全余量。下一次有效 usage 到来后重置增量。持久化锚点与对应消息位置，恢复后继续使用；压缩或内容替换后重建基准，避免继续显示旧大上下文。旧记录缺少锚点时必须明确回退估算，不能直接视为无压力。估算不是精确分词，模型/协议切换、图像与供应商 tokenizer 差异仍需保留边界保护。

## 服务端修复（已上线）

源目录：`D:/GIT/home/host/xywhsoft_ai`。

- SDK 定义统一的 32 MiB 请求正文上限；同时用于异步路由复制、上游 HTTP 发送、模型路由入口、JSON 读取与转发序列化检查。原来前三处代理检查之外，还有两处宿主 1 MiB 上限。
- 模型专用 JSON 读取显式设置正文与字符串预算，保留 20,000 个值的结构边界，不放宽通用后台 JSON 输入。
- 入口或转发重写后超限均返回 HTTP 413 `request_too_large`，消息标明实际字节、上限，并区分 HTTP 正文与模型 token。序列化失败不再混为通用 400 参数错误。
- 请求正文读取预留已受宿主接收限额约束的完整缓冲区，避免每 4 KiB 重新分配。大正文回归中原方式在约 15 MiB 处遇到分配失败并丢失正文，预留一次后 32 MiB 完整通过。

线上六处源码已部署，原生宿主程序和 xs.json 均未更换；账号、会话和计费数据库没有替换。
生产宿主热重载时 billing/mdo 插件启动失败，自动回退源码后路由仍未恢复；
确认没有运行中的模型收据后，尝试优雅重启，但旧进程排空停滞。
重新核对备份、候选源码、程序及配置哈希后，对该 xs.service 进程执行强制退出，
由 systemd 冷启动加载已在隔离实例通过测试的修复。新进程恢复 billing/mdo 为 running；
公开 HTTPS 的 1,050,076 字节匿名请求返回 401 login_required，表明旧 1 MiB 拒绝已解除；
32 MiB+1 请求返回明确的 413 request_too_large。模型推理服务未重启。
热重载失败和旧进程退出停滞是本次部署发现的限制，未在本轮宣称修复；后续插件部署应预留受控冷启动。

## 客户端实现

- 锁定兼容 SDK 提交 `4b0dddaa541243c0513ec1d2f9aba86dd1b5d37a`，
  由 `tools/dependencies/xs-context-governance.bundle` 提供；没有同步其他任务的未验证依赖。
- 以上次有效主模型调用的服务端 input+output 为用量锚点，累计锚点后的用户消息、
  工具结果和提示词净增长估算。移除配置上限推导的固定增长预留；每次请求前使用同一状态
  决定压缩与可用输出空间。只有 total、input/output 均为零的反馈不覆盖有效锚点。
- snapshot v4 添加可选 context_usage（fill_tokens、prefix_estimate、through_sequence、
  cached_input_tokens、profile_fingerprint），journal 添加 usage 操作；重启、备份恢复与
  兼容的完整分支保留锚点。同模型应用 profile 不清除锚点，切换模型或压缩后重新估算。
  旧会话缺少锚点时估算现存上下文，不能直接视为无压力。
- 产品上下文事件将精确基准、增长、预计输入、输入预算与压缩阈值投影给前端。
  圆环使用预计输入加当前草稿/图片估算，不再只显示上次输入；子 Agent 调用不覆盖主上下文。
  实际新增文本使用统一启发式，图片保守估算每张 4096 token。
- 估算仍非供应商精确 tokenizer，无法保证任意超长单次输入绝不越界；输出预留和安全余量保留。
