# grep 正则导致的会话恢复崩溃

用户提供的三个 Windows 转储均记录 `c0000005`、异常地址
`00007FFAFFFFFFFE`。弹窗对应 `lib/xrt.h:329662` 的 BBRE 单捕获 DFA
反向定位断言。转储名的时间使用 UTC，旁车文件系统时间为北京时间。

实际触发点是 x-lang 项目的“分析当前项目”会话中未完成的 `grep`：

```json
{"max_results":15,"path":"demo6/release/examples","pattern":"match .*"}
```

该调用从 2026-10-21 22:11 起没有完成事件。重新打开后恢复同一个调用，
因此再次崩溃。不是单纯读取或渲染历史文字失败，也不是模型连接问题。

## 根因及修复

在独立 C 程序中，`match .*` 搜索 `xmatch x`，或示例代码
`\t\txrtahomatch Match;`，即可稳定触发相同断言。无需会话、网络或模型。

DFA 曾找到有效匹配，但重复分支在匹配之后仍可存活；到达输入边界后的
哨兵状态可能不再接受。旧实现只返回最后状态的接受标记，丢掉此前接受的
位置，出现正向成功、反向失败。修复保留最后接受位置，反向与正向均遵循
同一规则，未找到匹配时不计算空指针差。断言仍保留。

- XRT 主线提交：`a539c579408fb0021456ad263249adfabb2e5a1a`。
- 产品兼容 xs 提交：`216f5445163ca30c815ad7d5d2da3b71cb2f6401`。
- `deps.lock` 固定基线及上游修复提交、单头哈希和源代码 bundle。
- 添加真实单文件程序的 `grep`、本地模型后续回复、连续两次重启回归，
  并加入正式发布门禁。

## 验证及交付

- XRT Regex 全套模块回归、OOM、单头与裁剪回归通过；新增 13 组搜索语义，
  包含触发输入、前后缀、贪婪、分支、空匹配及缓存重复使用。

- mdo 构建契约 16 项通过；固定依赖可从新 bundle 正常恢复。
- 开发版本与最终交付程序均通过三次原生 grep、模型后续回复和两次重启。
- 原故障会话的只读副本在隔离 Home 中恢复：仅重试指定的 grep，成功一次；
  用本地固定模型完成后续回复，重启两次仍可打开。原始会话文件哈希一致，
  未复制账号或凭据，未调用外部模型。
