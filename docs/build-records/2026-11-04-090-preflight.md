# mdo 0.9.0 发布前检查

日期：2026-11-04。版本：**0.9.0 / 05000900**。产品源码提交：`430f8a53`。

**结论：未放行，未发布。** 已完成本机可执行的自动检查和八种产物构建，确认了 Linux 启动失败和默认推理档位选择两个产品问题。历史运行时测试大量未同步，部分能力仍未得到有效覆盖；Android 没有连接设备，不能确认真机启动与升级。

本轮仅执行测试、构建与记录，没有修改产品代码。原有账号、会话及线上服务保持原状。供应商调用使用本地模拟服务。

## 需要修复的产品问题

### P1：Linux 四个产物无法启动

分别对 glibc/musl、桌面/服务版执行实际单文件程序，用独立临时 Home 和回环 HTTP 服务检查 `/api/v1/bootstrap`。四个进程均在服务装配时退出，尚未进入业务请求：

| 产物 | 首个启动错误 | 位置 |
| --- | --- | --- |
| glibc 桌面、服务版 | `include file 'unistd.h' not found` | `app/src/distribution/aria2.c:10` |
| musl 桌面、服务版 | `RTLD_NOW undeclared`，同时出现 `dlopen` 隐式声明 | `app/src/storage/home.c:1174` |

`aria2.c` 在所有非 Windows 平台直接包含 `unistd.h`，但当前 compact TCC SDK 没有提供该头。磁盘空间查询代码直接使用 `dlopen/dlsym/RTLD_NOW`，未保证独立、完整的声明；musl 静态构建还需要解决动态查找 libc 函数的可用性。只让编译器认识常量，并不能证明空间查询可用。

Android 也进入上述 POSIX 代码分支；本次重新构建的 Android SDK 资源表不含 `unistd.h`。这是同类启动风险的静态证据，**未在手机上验证，不能认定 APK 可以正常启动**。

修复方向：PID 与磁盘可用空间通过明确、稳定的宿主接口提供，或完整补齐 compact SDK 对这些操作所需的声明、符号和平台实现。避免 TCC 代码依赖未提供的系统头、unity 包含顺序或静态 musl 不支持的动态查找。修复后必须重新执行完整应用的 TCC 装配、下载空间预检，以及四个 Linux 产物启动；Android 补真机验收。

证据：`.build/preflight-090-20261104/linux-smoke.json`、四份 `linux-*-smoke.log`、`.build/android/native/tcc_sdk_resources.c`。

### P2：省略推理强度时不能适配模型默认值

条件：全局档位为 `medium`，配置一个仅支持 `none`、默认也是 `none` 的个人模型。用实际 0.9.0 Windows 候选创建会话：

| 请求 | 结果 |
| --- | --- |
| 指定模型，省略 `reasoning_effort` | HTTP 422，`model_profile_reasoning_unsupported` |
| 同一模型，显式指定 `reasoning_effort: "none"` | HTTP 201 |

根因位于 `app/src/agents/runtime.c:1341`：未指定时继承 Agent/全局档位，随后直接验证，未在全局默认值不适用时回退到模型默认值。影响原生接口、SDK 和依赖默认值创建任务的扩展；界面显式提供有效档位的路径不受这次复现影响。

修复方向：保留调用方及 Agent 显式设置的严格验证；对隐式继承的全局偏好检查模型是否支持，不支持时采用模型默认值。不能为了让旧测试通过而接受显式请求的不支持档位。

证据：`.build/preflight-090-20261104/reasoning-default-proof.json`。该复现没有模型网络调用。

## 门禁与夹具缺口

标准门禁首先在 `test_agent_authoring_runtime.py` 停止：共享夹具仍复制已删除的 `default-home/modules/agents/builtin_default.c`。随后继续执行其他独立检查并保留每项结果，没有修改产品行为或放宽原测试断言。

失败入口中反复出现以下情况，导致相应功能没有得到有效验证：

- 从已清空的默认模型列表取第一个元素，或继续请求旧内置 Ornith；部分恢复夹具因此根本没有创建测试会话。
- 测试模型只声明 `none`，调用方却显式请求 `medium`。
- 部分 C 夹具只编译子系统，遗漏 `MdoApplicationPluginHasFile`、`MdoExtensionsEditableSource` 等当前依赖。
- 继续使用已淘汰的扩展工具包目录、平铺扩展文件、JSON 编辑/分发协议，以及旧模型 schema。
- 部分测试没有复用传入的 SDK，尝试寻找已失效的旧 worktree。

当前模块目录专项的失败也已定位：夹具要求工具总数恰为 1，而当前加载的是 22 个内置工具加 1 个自定义工具。保持产品代码不变，按 `user.fixture` ID 选择目标工具后，资源读取、Agent/SubAgent 执行、继承、头文件更新、停用与卸载断言全部通过。原专项的失败记录仍保留，没有计入原始通过数。

另有一次打包 WebSocket 检查报“只读连接改变了 Home”。原断言没有记录变化文件；补充差异捕获后，三次独立复查均为空差异。该间歇失败尚未确定根因，不能声称已修复；应为夹具增加精确差异证据，并区分受保护数据与后台缓存写入。

修复门禁时应为仍存在的功能补齐当前夹具，淘汰已删除功能的检查，并把当前目录式原生专项接入正式门禁，不能通过重新引入旧产品配置或取消严格验证来使检查通过。
