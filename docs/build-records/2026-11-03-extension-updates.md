# 扩展后台更新检查与统一更新入口

## 完成的行为

- 启动完成约 5 秒后，由原生后台线程检查更新，无需打开设置或商店。正常每 6 小时检查一次；每 30 秒检查本机扩展清单是否改变，改变后重新检查。网络失败按 1、2、4、8 分钟退避，保留上一次可用结果。
- 九类扩展共用一个通知区图标与数量，点击打开公共弹窗，列出名称、类型、提交者、当前及新版本、下载大小、说明，支持逐项更新、全部更新和重新检查。
- 本机列表直接显示更新按钮，商店中的已安装条目也可直接更新。任务进入统一下载队列，关闭弹窗或切换页面不会终止已接收的任务；完成后更新清单和按钮刷新。
- 常规更新一次点击。新增依赖或声明的权限／影响范围改变时，复用依赖计划确认窗口；阻塞计划显示具体原因。
- 更新依据是同一线上作品的扩展身份、发布序号与包 SHA-256，不比较展示版本字符串。手动添加且没有线上关联的内容不参与自动检查；停用的已安装扩展仍检查更新，更新后保持停用。
- 后台缓存位于 Home 相对路径 `data/cache/extension-updates.json`。查询仅发送已关联的公开扩展标识与平台，不发送本机路径、模型凭据或 MCP 私有配置。

## 批量更新和故障处理

客户端先生成并固定各根扩展的检查计划，原生服务再次核对。共同依赖版本不一致时在任何安装前拒绝整批计划；一致的共同依赖只下载一次。每个根扩展复用现有事务、失败回滚、运行时就绪检查及临时错误最多五次重试，互不相关的根失败不撤销已经成功的根。

批量收据记录每个根的结果，页面据此分别显示成功或失败。已完成、执行中或结果未知的收据不会被“全部更新”再次提交；结果未知时引导查看已有下载任务。原有启停状态、扩展目录外的用户数据和本机私有配置按现有安装事务保留。

## 接口

- 平台只读接口：`GET /api/v1/mdo/extensions/updates?refs=...&platform=...`。一次最多 24 个不重复标识，只返回当前已公布的版本，忽略不存在、私有、撤回的作品。
- 本机缓存：`GET /api/v1/ecosystem?scope=updates`。
- 本机操作：`POST /api/v1/ecosystem` 的 `updates`、`check_updates`、`update_batch`，复用 SDK 操作生命周期与全局下载队列。每批最多 128 个固定计划。

## Android 的交付边界

原生外部工具继续仅随 full APK 交付。打包时在现有 `assets/mdo-runtime.json` 的每个工具条目加入实际目录 ZIP 的扩展 ID、名称、版本、描述、大小与摘要，仍只包含原有八个工具。

平台按当前已发布 full APK 的实际索引回答 Android 原生工具更新查询，不使用桌面／独立 ZIP 的最新版本代替。界面显示“更新完整版”，复用应用更新和下载任务入口，不把这类条目加入普通扩展的批量安装。

本次同时补齐平台 APK ZIP 读取器对签名块前零填充的处理，与客户端已有实现一致。现网 0.8.6 full APK 尚无新增的逐工具元数据，查询不会推测其中存在新版 Python；下一次发布新 full APK 后，实际包含的新工具版本才会被提示。
