# 跨标签提交的持久化边界

## 已复现的问题

2026-09-27 在根目录单文件版的隔离 Home `.build/mdo-packed-docks-o34ffnp5`，使用 `python tests/manual_packed_docks_qa.py --run-delay-ms 3000 --slow-ms 2000` 打开同一会话的两个真实浏览器标签。A 输入 `TWO TAB DIRECT A`，B 输入 `TWO TAB DIRECT B`，随后两页几乎同时点发送。A 留下一轮完整消息和一次成功运行；B 显示“等待入队确认”和草稿 revision 冲突，但服务端草稿的 `submissions`、待发队列均为空。刷新 B 后，其待发卡和输入原文同时消失。代理计数为一次队列 POST、一次运行 POST，两页均无脚本错误。

原因是 `submission-controller.js` 在 `draft-store.js` 的 revision 条件写入成功之前就调用 `onPersisted` 清空输入框。B 的写入因另一标签修改 `draft.json` 收到 `draft_conflict`；B 的待发项只存在于页面内存，却按持久待核对项呈现。刷新后服务器没有依据恢复它。服务端在同进程下通过锁和 revision 正确拒绝旧快照，缺的是提交意图的独立持久化与客户端冲突语义。

## 落地约束

1. 每次 Enter 生成稳定的提交 ID。输入被清空并宣称“已待发”之前，服务器必须已经把该 ID、原文、附件引用及优先级写入 mdo Home。写入结果不明时只能以同一个 ID 查询或重试，不得生成新 ID 自动重发。
2. 提交意图的新增、状态推进和移除必须按 ID 原子执行，不能以一个标签读到的旧 `submissions` 数组覆盖另一标签的新项。仍需保持最多 20 项、总文本上限、附件归属校验和队列消费凭据。
3. 原子新增应在现有 draft 锁内完成，重复 ID 且负载相同返回既有结果，重复 ID 但负载不同拒绝。`prepared → posting` 要在调用队列 API 前持久化；只有查到队列项或消费凭据才能删除提交意图。网络响应丢失不得自动推断为失败。
4. 普通草稿文本的 revision 冲突须与提交意图区分。若另一标签改变了文本，不覆盖远端文本，也不把本地未保存文本伪装成可刷新恢复。冲突后的编辑需要明确的保留与合并入口。
5. 先写 API 运行探针覆盖并发新增、幂等重试、状态转移、容量和附件校验，再以两张打包页面重放上述步骤，核对两条文本最终各有明确去向；刷新不能使任一条静默消失。Windows/Linux 继续跑有界门禁，不做压力或高负载测试。

## 修复与回归

会话草稿新增 `POST /draft/submissions`：在草稿锁内按稳定 ID 追加 `prepared` 意图；相同 ID/负载幂等返回，负载不同返回 409，仍校验总文本、容量与图片归属。`PUT /draft/submissions/{id}` 和 `DELETE /draft/submissions/{id}` 按 ID 原子推进状态、移除意图，不再把旧标签的整个数组写回。移除意图时，若草稿文本及附件仍与该意图完全相同，同一事务清空它们；人工恢复未发送内容在移除后重新持久化。普通草稿 PUT 失败时，页面用原 ID 原子追加或 GET 核对，只有确认服务端已有该意图才清空输入。彻底断网且无法核对时保留输入原文，并提示人工核对。

`tests/test_api_runtime.py` 覆盖两请求同时新增、重复 ID、冲突负载、附件校验、状态转移、删除幂等、匹配草稿清理及旧 revision 拒绝；`tests/test_submission_controller.mjs` 覆盖旧标签追加、PUT 响应丢失、无持久确认时保留输入、人工恢复。
