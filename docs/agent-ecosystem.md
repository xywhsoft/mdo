# Agent / SubAgent 独立生态

Agent 与 SubAgent 分别提供本机、商店两个入口，共用作品、投稿、审核和安装协议。配置式与 C 角色拥有相同的生态流程，不需要先创建组合包。

## 使用流程

1. 在对应本机列表创建配置，或把独立 C 程序放到 `modules/agents/<id>.c` / `modules/subagents/<id>.c`。单文件 C 入口可使用 `mdo/agent.h` 的 `MDO_AGENT_MODULE`；多角色模块继续由扩展包管理。
2. 点击“分享到创作中心”，填写名称、版本、说明、作者、版权、许可和实际验证过的平台。检查最终上传的配置、源码及依赖。可以私有保存，或附源码来源、构建与权限说明申请公布。
3. 创作中心 `/mdo/creator?kind=agents|subagents` 管理作品、版本、公布申请、下架和删除；后台对应独立页面 `/admin/mdo/extensions/agents|subagents`，采用 `_component + layui table`，切换待审核、已公布、未公布。
4. 商店详情显示作者、提交者、版权、使用方式、源码、自有文件、历史及安装计划。配置式角色直接确认安装；含 C 的角色必须额外确认源码信任。C 在 mdo 进程内运行，编译注册也可能执行代码。
5. 安装后 Agent 出现在会话角色选择中；SubAgent 由允许委派到它的角色调用。下载内容只允许启停、更新和卸载，不允许编辑、复制、导出或再次分享。

作品配额沿用创作中心：普通用户 3 件 / 每版本 10 MiB，创作者 20 件 / 每版本 100 MiB；审核附件计入同版本容量。新版本独立审核，旧公开版本在审核期间继续可用。

## 一个角色的分发单元

外层继续使用 `mdo.extension.v2`，单个作品的 `resources` 必须恰好一项，`kind` 为 `agents` 或 `subagents`。配置正文统一导出为 JSON，仍使用 `mdo.agent.v1`。最低客户端内部构建号为 **70000009**，与语义版本码分开。

```json
{
  "kind": "agents",
  "id": "reviewer",
  "content": "{\"schema\":\"mdo.agent.v1\",\"name\":\"审查员\",\"mode\":\"both\",\"tools\":[\"read\"],\"prompt_file\":\"reviewer/assets/prompt.md\"}",
  "files": [{"path":"assets/prompt.md","base64":"UmV2aWV3IGNhcmVmdWxseS4="}]
}
```

- 配置安装到 `<kind>/<id>.md`，JSON 内容可由本地角色解析器直接读取。
- `assets/<relative>` 安装到 `<kind>/<id>/assets/<relative>`。`prompt_file` 和上下文 `file` 必须引用所附的同角色目录文件。导出重写路径，只读取作者明确引用的文件，不导出渲染后的上下文、项目目录、记忆、会话或凭据。
- C 角色设置 `code:true` 并附 `program.c`，安装到 `modules/<kind>/<id>.c`，使用与配置相同的角色 ID。附件仅接受有界 UTF-8 文档或源码，不分发宿主二进制。当前每文件最多 128 KiB、每角色最多 128 个附件。
- `mode:both` 允许同一个角色用于主会话及委派任务，作品仍归属于作者选择的一个商店分类。
- 独立 C 角色从已发布的本地模块描述符获得展示信息；GET 和导出不会执行生命周期回调。停用的独立 C 角色可管理，重新启用并验证后才显示分享入口。
- “导出”得到 `.role.json`，包含配置与自有文件，可在对应本机页面导入。含附件的导入走同一个安装计划和持久事务；不会把附件丢给普通单文件编辑器。

## 依赖和设备差异

配置中的 `extends`、`skills`、固定 `model` 和 `mcp_servers` 作为必需依赖声明；内置基类和 `model:inherit` 不要求额外安装。安装计划检查本机目录，缺失或停用的必需依赖阻止落盘，并提示先配置它们。不会自动把其他体系组合进作品，也不会借发布流程上传模型密钥或 MCP 授权。

委派允许列表作为可选角色选择器，按本机实际子角色目录检查。知识库和外部工具的可选选择器在任务实际作用域中解析，安装预览显示“运行时按选择器解析”，不误报为缺失。

不同设备的固定模型 ID、MCP 连接名可能不同。作者优先使用继承模型并说明所需能力；确需固定引用时，下载者先在设备上配置对应 ID。商店不会改写作者源码来掩盖不匹配。

## 安装、更新与兼容

客户端和平台编译同一套纯格式校验头；服务器审核与预览不编译 C、不连接 MCP。旧客户端按最低构建号过滤新角色作品。历史组合包保留原记录与通用入口，不混入两个独立角色商店。

配置、C 源码、附件、安装收据共用持久回滚日志。更新前检查原文件摘要；C 编译、角色绑定或重载失败时恢复全部文件与收据。停用状态跨更新保留，正在运行的会话继续持有原代码 generation。卸载时任一角色文件被本机修改，将保留整套角色，避免留下失去配置或源码的零散附件。

## 验证入口

- `tests/test_role_package_runtime.py`：原生角色导出、独立 C 管理、依赖计划、C 信任、编译失败回滚、停用更新、整套保留及旧构建拒绝。
- `tests/test_role_store_runtime.py`：两个隔离 TCC 服务完成私有投稿→申请公布→审核→分类商店→下载安装→更新，以及下载的配置主角色调用下载的 C 子角色。
- `home/tests/test_mdo_single_resources.py --roles`：网站独立分类、配额、审核、旧客户端过滤和平台管理合同；使用不可编译源码确认网站不会执行投稿。

本地角色开发 API、回调及配置细节见 [角色开发指南](agent-authoring.md)。
