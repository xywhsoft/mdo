## 接收契约与修复

xs 在请求正文完整到达后才调用 `RequestProc`。xrt TLS 发布未消费的明文前缀后，会暂停继续发布，要求上层消费或调用 `xrtTlsStreamReadMore`。原 xs 驱动保留部分正文等待剩余字节，却没有请求继续接收，双方因此互相等待。较大的正文另受到默认 TLS 明文队列 256 KiB 的容量约束。

修复位于 xs：

1. 保留不完整头部、正文或 drain 前缀时显式调用 `xrtTlsStreamReadMore`；失败则结束连接，避免再次挂住。空缓冲继续走普通消费路径，接管连接保留业务自己的接收回调。
2. 每个 HTTP TLS 监听器使用独立的上下文快照，明文容量对齐有效 `recv_limit`，另容纳一条 TLS 记录，使超限请求能够到达 HTTP 拒绝边界。容量计算检查溢出，失败路径释放临时所有权；不预分配整个窗口。

源修复分别来自 `c840d8c`、`483d753`。实际部署源码提交为 xserver 的 `ff4df050dbde6b4a681fc3fa5a277dc383d20a65`，包含线上原有 `16bceff` 的连接接管空闲修复。故障属于 xs 未遵守底层接收契约，当前证据不支持修改 xrt 核心或认定会话存储损坏。
