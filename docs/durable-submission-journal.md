# 连续输入的便携提交日志

## 目标与现状

Enter 应立即给出“已接收输入”的反馈，后续输入仍可继续；刷新、WebView 退出和进程重启不能让尚未确认的文字或图片静默消失，也不能把可能已执行的请求自动重发。所有持久状态留在 `mdo.exe` 所在的便携 Home，不依赖浏览器的 localStorage/IndexedDB。

既有会话现在把输入意图依次保存在会话 `draft.json` 的 `submissions` 列表中，再逐条写入队列 `staged` 项。每项有稳定 ID、原文、图片 ID、优先发送标记和 `prepared/posting` 状态；下一条可编辑草稿仍在独立的 `text` 字段。服务端 `queue.json` 已能持久保存入队后的消息，但队列 ID 在项被移除后不再提供去重证据。新任务创建和 `submissionLanes` 的后续暂存项仍只在页面内存；首轮运行 POST 也没有持久请求 ID。因此“队列为空”不能证明消息没有执行。

## 持久状态与顺序

会话队列新增 `staged` 状态，作为已落盘、尚未获准派发的输入意图。文件 schema 4 兼容读取 schema 1/2/3；每项继续使用随机 32 字符十六进制 ID、原文、至多四个图片 ID 和优先标记。既有 20 项、192 KiB 正文总量及图片引用校验保持不变。状态流为：

```text
编辑中的草稿 → staged → pending → sending → 运行结果及队列移除
                          └───────────→ 失败后人工核对
```

`POST /queue` 的可选 `stage: true` 只写入 `staged`，不允许派发。相同 ID 和内容在项仍存在时返回现有项；不同内容仍返回冲突。`PUT /queue/{id}` 只允许 `staged → pending`、`pending → sending`、`sending → pending`；最后一种只供用户核对后重试。`staged → sending` 不允许跳过提交边界。删除、图片引用保护、会话归属与普通队列项一致。

既有会话的前端接线先把每条输入加入便携 Home 的有序日志，确认落盘后清空匹配的输入框内容。串行提交器只把队首改为 `posting` 并写入 `staged`；随后输入保持 `prepared`，即使前一条 POST 未返回也可继续按 Enter。队列确认相同 ID 与内容后清除队首快照，再把 `staged` 提升到 `pending`，由统一派发器启动运行。刷新后若前一项停在 `staged`，后续 `prepared` 不越过它，用户可手动继续。队列 POST 结果不明时不自动重发，`sending` 仍要求人工核对。队列项消失但缺执行关联时，不把队列空置当作未执行证明；快照保留并显示核对入口。草稿写入失败时不发队列 POST。

日志最多保存 20 条、正文合计 192 KiB，每条正文不超过 64 KiB；达到上限时停止接收新提交，但输入框内容继续保留。旧 schema 4 的单条快照按 `posting` 导入，要求核对后再恢复。API 暂时保留旧 `submission` 首项投影及写入兼容，供旧客户端升级。

新任务在会话尚未创建时仍以全局草稿保留文本；创建会话后才迁移到该会话队列。要关闭“服务端已创建会话但创建响应丢失”的重复创建窗口，仍需给创建请求加入持久客户端 ID 和服务端去重记录。未完成该边界之前，不应把新任务强制刷新称为完全可靠。

## 恢复与核对边界

队列项可见时，按 ID 恢复其顺序和状态；`staged` 表示服务端已保存意图，允许继续提交流程。`sending` 不能凭页面刷新改回 `pending`，因为运行可能已经启动。队列项已经消失时，仅凭当前队列也不能推断它从未执行；未来应把队列 ID 与运行启动及持久会话事件关联，并为已移除 ID 留下可查询的消费凭据。在这两项完成前，任何不确定请求只展示原输入和核对操作，不进行自动重试。

验收使用少量隔离 Home 合成回合：正常首条与连续三条的顺序；`staged` 写入前后的刷新；提升响应丢失；运行启动响应丢失；图片引用在 staged、pending、sending 各状态下的保护；切换会话后异步结果不改写新会话；新任务创建响应丢失。每个结果核对服务端文件、运行 POST 次数与页面提示，不使用压力或高负载测试。

已交付服务端 `staged` 状态、草稿 schema 5 有序日志和既有会话的串行提交器。前端支持前一条入队响应等待时继续发送、刷新后恢复有序快照、明确拒绝后的人工核对重试，以及已落盘 `staged` 前驱的顺序屏障。Node 模块测试覆盖并发 Enter 和前驱屏障；隔离打包页分别验证延迟 POST 时两次 Enter 后刷新、前驱手动继续，以及首条被明确拒绝后刷新并重试，最终两条消息按序进入时间线。仍需新任务创建去重、队列项消费凭据和运行启动去重。这些边界完成前，不宣称连续输入在所有响应丢失情况下都已完全可靠。
