# 连续输入的便携提交日志

## 目标与现状

Enter 应立即给出“已接收输入”的反馈，后续输入仍可继续；刷新、WebView 退出和进程重启不能让尚未确认的文字或图片静默消失，也不能把可能已执行的请求自动重发。所有持久状态留在 `mdo.exe` 所在的便携 Home，不依赖浏览器的 localStorage/IndexedDB。

既有会话现在把输入意图依次保存在会话 `draft.json` 的 `submissions` 列表中，再逐条写入队列 `staged` 项。每项有稳定 ID、原文、图片 ID、优先发送标记和 `prepared/posting/rejected` 状态；下一条可编辑草稿仍在独立的 `text` 字段。`rejected` 只用于入队阶段明确返回 `queue_full`，表示服务端拒绝了该次入队；其它响应丢失或提升失败仍按结果不明处理。新任务在创建前把稳定会话 ID 和有序输入保存在全局草稿，创建后迁移到会话草稿。服务端 `queue.json` 已能持久保存入队后的消息；处于 `sending` 的项获准启动运行后，还会保存 `run_id`。队列 ID 在项被移除后仍不提供去重证据，因此“队列为空”不能证明消息没有执行。

## 持久状态与顺序

会话队列的 `staged` 状态是已落盘、尚未获准派发的输入意图。文件 schema 5 兼容读取 schema 1–4；每项继续使用随机 32 字符十六进制 ID、原文、至多四个图片 ID 和优先标记。schema 5 仅允许 `sending` 项附带运行启动后的 `run_id`。既有 20 项、192 KiB 正文总量及图片引用校验保持不变。状态流为：

```text
编辑中的草稿 → staged → pending → sending → 绑定 run_id → 运行结果及队列移除
                          └───────────→ 失败后人工核对
```

`POST /queue` 的可选 `stage: true` 只写入 `staged`，不允许派发。相同 ID 和内容在项仍存在时返回现有项；不同内容仍返回冲突。`PUT /queue/{id}` 只允许 `staged → pending`、`pending → sending`、尚无 `run_id` 时的 `sending → pending`；最后一种只供用户核对后重试。`staged → sending` 不允许跳过提交边界。删除、图片引用保护、会话归属与普通队列项一致。

运行 POST 可选带 `queue_item_id`。服务端启动前要求该项仍为 `sending`，正文和图片 ID 与请求完全一致，且没有已绑定的运行；启动后将 `run_id` 写回队列，再返回成功。重复请求若能看到已绑定的 `run_id`，返回 `queue_run_started`，不会发起第二轮。绑定写入失败时返回 `run_receipt_unavailable`，客户端按结果不明处理，不能自动重试。刷新后带 `run_id` 的队列项明确提示“服务端已接受运行”，禁止改回 `pending`；用户核对时间线后可手动移除。

既有会话的前端接线先把每条输入加入便携 Home 的有序日志，确认落盘后清空匹配的输入框内容。串行提交器只把队首改为 `posting` 并写入 `staged`；随后输入保持 `prepared`，即使前一条 POST 未返回也可继续按 Enter。队列确认相同 ID 与内容后清除队首快照，再把 `staged` 提升到 `pending`，由统一派发器启动运行。刷新后若前一项停在 `staged`，后续 `prepared` 不越过它，用户可手动继续。队列 POST 结果不明时不自动重发，`sending` 仍要求人工核对。队列项消失但缺执行关联时，不把队列空置当作未执行证明；快照保留并显示核对入口。草稿写入失败时不发队列 POST。

会话草稿 schema 6 支持 `rejected`；旧 schema 1–5 可读，旧 schema 4 的单条快照按 `posting` 导入。全局新任务草稿继续使用独立的 schema 6 结构，且不接受 `rejected`，因为它描述的是会话队列的入队结果。日志最多保存 20 条、正文合计 192 KiB，每条正文不超过 64 KiB；达到上限时停止接收新提交，但输入框内容继续保留。API 暂时保留旧 `submission` 首项投影及写入兼容，供旧客户端升级。

新任务首条输入现在把稳定会话 ID、项目、标题和模型配置作为 `new_task` 元信息，与有序 `submissions` 一起写入全局 `data/draft.json`（schema 6）。首条快照 ID 同时用作 `client_session_id`；创建 API 首次返回 201，同 ID、同配置重试返回 200，冲突或目录元数据不完整时返回 409。页面在创建响应等待期间继续接受后续输入，每条都先加入全局便携日志。创建成功后先把元信息置为 `copying` 并落盘，再把快照复制到新会话草稿，确认会话草稿落盘后才清除全局记录；会话草稿随后沿既有串行提交器入队。创建响应丢失时可按稳定 ID 查询或重试，而不创建第二个会话。刷新后若全局日志处于 `copying`、但新会话草稿缺少队首，页面要求人工核对，避免凭空队列重新发送已执行的内容。

创建 API 明确返回 4xx 时不把它当作响应丢失：页面保留全局快照，解锁模型、思考强度和权限选择。用户调整后重试会在一次草稿写入中更换稳定会话 ID、首条快照 ID 和创建配置，再发起创建；后续快照与原有顺序保持。创建结果不明时仍锁定原配置并按原 ID 核对，绝不擅自换 ID。

## 恢复与核对边界

队列项可见时，按 ID 恢复其顺序和状态；`staged` 表示服务端已保存意图，允许继续提交流程。`sending` 不能凭页面刷新改回 `pending`，因为运行可能已经启动；有 `run_id` 时能查明已接受的运行。队列项已经消失时，仅凭当前队列也不能推断它从未执行；未来仍须为已移除 ID 留下可查询的消费凭据，避免另一页面先消费队列项、原页面却看不到记录。启动成功但绑定落盘失败也尚无原子恢复机制。对于这两种边界，任何不确定请求仍只展示原输入和核对操作，不进行自动重试。

验收使用少量隔离 Home 合成回合：正常首条与连续三条的顺序；`staged` 写入前后的刷新；提升响应丢失；运行启动响应丢失；图片引用在 staged、pending、sending 各状态下的保护；切换会话后异步结果不改写新会话；新任务创建响应丢失。每个结果核对服务端文件、运行 POST 次数与页面提示，不使用压力或高负载测试。

已交付服务端 `staged` 状态、会话草稿 schema 6 有序日志及明确拒绝状态、全局草稿 schema 6 的新任务元信息、既有会话与新任务的串行提交路径、创建 API 的稳定会话 ID 去重，以及仍在队列中的运行关联。前端支持创建和入队响应等待时继续输入、刷新后恢复有序快照、明确失败后的人工核对、已落盘 `staged` 前驱的顺序屏障，以及运行响应丢失后展示已接受的 `run_id` 状态。图片优先的新任务也先记录稳定会话 ID，创建响应丢失时查询该 ID；文件本体只有上传成功后才能在会话中恢复，若浏览器在上传前关闭，用户须重新选择图片。Node 模块测试覆盖并发 Enter、新任务迁移、创建冲突、前驱屏障和明确拒绝后的刷新恢复；隔离打包页验证连续输入恢复、明确 `queue_full` 后无自动重发且可恢复原文、图片优先创建响应丢失后仍只有一个会话，以及运行响应丢失后刷新保留已接受状态。仍需已消费队列项的凭据、启动与绑定的原子性和并发启动去重；这些边界完成前，不宣称所有响应丢失路径都已完全可靠。
