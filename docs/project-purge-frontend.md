# 项目清除的前端操作与恢复

项目设置的“核对清除范围”先显示只读候选清单，然后通过“继续核对清除”进入独立确认
弹窗。取消注册仍是独立操作。彻底清除覆盖原项目在 Home 中的定义、会话、
记忆、草稿和关联计划等已列出的数据；工作区源文件、其他项目及共享审计保留。
这项操作不能通过产品撤销，确认弹窗明确说明这一点。

## 确认与执行

打开清单、刷新清单、打开确认弹窗和按 Esc 都不保存或执行请求。确认弹窗
默认聚焦取消按钮，只有输入与当前项目 ID 完全一致时才能提交。弹窗沿用
移动端可见视口规则，操作栏固定，内容区可滚动；执行期间禁用输入与取消，
重复提交合并为同一次操作。

提交前核对清单的绑定、强 ETag、候选路径和统计，并要求运行态及诊断计数
均为零。客户端还要求消息操作、附件、配置切换、任务准备和队列派发已结束，
并保存全部已加载的脏草稿。保存失败或仍有在途写入时，不生成请求编号。
这不是独占授权：服务端继续按 [事务协议](project-purge-transaction.md) 重新
取得独占、核对绑定并扫描实际目标。

准备结束后生成一个安全随机编号，立即暂停本页普通写入，再保存并确认
便携意图。执行前重新读取该意图及原结果，只使用原编号、原版本和原定义
创建时间。丢失保存或执行响应时保留原编号并查询，不自动再次执行；重新
载入也不自动执行。恢复卡的“继续核对清除”要求已保存的原意图尚未被
接受且绑定一致；新版本或重建的同名项目不能沿用旧确认。

## 结果与页面收敛

未知或 pending 结果保持暂停和原编号。取消请求会持久预留原编号的 abort，
只有核对该终态后才允许明确移除意图。HTTP 失败不等于没有提交，错误携带
的提交事实和后续查询均须严格校验；已知提交事实不能被矛盾响应覆盖。

已提交且不要求宿主恢复时，显示“确认完成并重新载入”。此操作要求本地
没有在途动作或未保存草稿，重新核对原终态后确认移除意图，并保持本页暂停
直到真实页面重新载入。受影响的返回导航记录被清除；若当前工作区属于被
清除项目，转到项目设置。不在旧页面恢复自动保存、迁移或派发，也不保留旧
项目作为当前选择。无关项目的已保存数据保留。

存在未保存内容时提供复制快照与明确重新载入，不自动丢弃。复制仅覆盖已
加载草稿的文字、图片 ID、配置与待发快照，不包含图片二进制或未加载记录。
若结果要求宿主重启，明确提示重启程序；页面刷新不代表宿主恢复成功。
确认只移除便携意图，永久结果凭据仍保留。

其他旧标签页和旧宿主的迟到 HTTP 写入由 [页面代与写入准入](http-write-admission.md)
拒绝，即使意图已经被另一页移除。本地暂停不是全局权限边界；后台和 C 写入
继续依赖项目生命周期租约与存储锁。

## 验证边界

`tests/test_project_purge_execution.mjs` 验证排空、原编号、丢响应、绑定变化、
终态确认、暂停及未保存草稿。`tests/test_project_purge_frontend_runtime.py`
在七个小 Home 中让正式前端模块走真实 xs/TCC HTTP，验证正常提交、丢保存/
执行/确认响应、回滚、取消和排空失败，并核对目标与保留数据的物理字节。
故障仅注入复制源或客户端响应，不调用外部模型。

打包页确认弹窗的实际提交使用 `manual_packed_purge_preview_qa.py --cancel-before-execute`：
复制的 C 夹具在执行之前持久预留零目标 abort，任何
点击都不能移除预置内容。它验证前端准备、显式执行及结果焦点，不是生产
清除成功的 GUI 证据。另一个未修改的最终包在页面打开前通过正式 API 清除
自有合成项目，再验证完成确认、重新载入和无旧数据写回。

桌面及 320×350 浏览器视口已核对默认取消、输入门、Esc 返回、40px 按钮、
内部滚动、结果焦点、无横向溢出和无脚本错误。原生窗口完整清除点击、实体
移动设备、Linux/macOS 本阶段未新增验收。只做有界测试，不做压力或高负载测试。
