# 运行中切换后续消息配置

状态：分阶段实施。2026-09-28 对照 `app_bak/wwwroot/src/ui.js` 的输入区和当前单文件版，确认这是旧版操作逻辑尚未恢复的一项。草稿、提交意图及队列项的配置快照合同已落地；原子启动和前端选择器仍待实现。

## 现状与目标

旧版在当前任务运行时保留模型、思考强度和权限入口，选择模型还会更新所选会话的配置。当前 `app/web/js/features/chat/composer-profile.js` 在 `runActive` 时禁用三个入口；隔离单文件 Home `.build/mdo-packed-docks-bpncv2lo` 在 390×500 运行 `SLOW UI` 时确认输入仍可编辑、三个选项均为 disabled。服务端 `MdoSessionSetProfile` 要求会话处于 active 且 idle，直接去掉前端禁用会让选择在服务端被拒绝，不是修复。

恢复后的行为应当是：当前运行继续使用启动时的配置；用户运行中调整输入区选项，看到明确的“下次任务生效”状态，可以继续输入与排队；每条待发送消息在提交时冻结其模型、思考强度和权限，后续调整不改写已经入队的消息。刷新或切换会话后，尚未发送的选择与每条消息的配置仍可追溯。无效模型、能力不兼容及配置保存失败应明确报错并保留原消息，不得静默回退到别的模型，也不得提前改写历史。

## 持久化与协议边界

1. 会话草稿保存“下一条消息的配置选择”；提交意图保存同一配置快照。现在 `draft.json` 为 schema 6，必须继续读取旧文件，新增字段应有严格长度、枚举及完整性校验。不要把它放在浏览器 `localStorage`，便携 Home 是可恢复事实来源。
2. 队列项保存不可变的配置快照。现在 `queue.json` 为 schema 6；旧项没有快照时沿用当前会话配置。队列 POST 的同 ID 幂等比较须包含配置，避免另一页面用同一 ID 改写将要执行的模型或权限。队列 GET 应返回快照，供页面显示和核对。
3. 对绑定队列项的运行，服务端须在独占会话启动的同一事务边界内检查队列快照、校验模型能力、应用有效配置并开始运行。浏览器先 PUT 会话 profile、再 POST run 的两步方案有竞态：另一个标签可能在两次请求之间启动不同队列项。图片能力必须按该项的有效模型判定。运行已被接受后的凭据仍按现有 `starting`/`accepted` 规则处理。
4. 会话运行中调整的配置只作为后续意图保存，不能改变运行中的 Agent。没有排队项时，新选择仍保留在会话草稿；会话空闲后可通过已有 profile API 落地，或者在下一次绑定运行时原子应用。界面必须区分会话当前配置和后续意图，不能把尚未落地的选择呈现为已完成更新。
5. 跨标签提交沿用已有草稿 revision、稳定提交 ID 和核对屏障。同一队列项只能执行其冻结配置；不确定响应不得通过更换 ID 或模型自动重试。新任务的首次提交需要继续把创建时的 Agent、模型、思考强度、权限一起固定。

## 实施顺序与验收

1. 先扩展草稿、提交意图与队列的读写合同，含旧 schema 迁移、严格验证、幂等冲突和配置缺省测试；保持当前 UI 禁用直到服务端运行边界完成。
2. 将配置应用纳入绑定队列项的服务端启动流程，覆盖不同标签同时发现队首、不同配置的连续两项、运行忙碌、启动前明确失败与启动结果不明。任何失败都不得让后续项抢跑。
3. 再开放前端运行中的三个选择器，显示后续生效状态，持久化选择并在提交时快照；切会话、刷新、归档只读状态和 `/model` 命令须一致。
4. 用生产模块浏览器夹具及隔离单文件 Home 验证一条运行中、两条不同配置排队消息的最终运行记录和页面回放；检查服务端队列、草稿、凭据、浏览器脚本错误和单文件零旁路写入。Windows/Linux 仅做有界发布门禁，不做压力或高负载测试；原生移动端另行验收。

在上述事务边界完成前，不单独解锁前端选择器。

## 第一阶段：草稿与提交意图

`draft.json` 已升级为 schema 7，并继续严格读取 schema 1–6。可选 `composer_profile` 保存下一条消息的完整模型、思考强度和权限选择；PUT 未提供该字段时保留原值，显式 `null` 清除。每条 `submissions` 的可选 `profile` 是完整且不可拆分的快照，携带该字段的重复 ID 仅在配置相同的情况下视为幂等。浏览器草稿存储往返保留这些字段，且加载前先编辑文字不会擦掉远端已保存的选择。旧数据没有快照时仍保持原 API 响应形状。

第一阶段只建立草稿持久化合同；队列传递见下节。运行中三个选择器继续禁用，直到绑定运行的原子配置应用完成。

## 第二阶段：队列快照

`queue.json` 已升级为 schema 7，仍读取 schema 1–6。队列 POST 的可选 `profile` 必须是完整三字段对象；相同 ID 若模型、思考强度或权限不同，返回 `queue_id_conflict`。队列 GET、状态转换与磁盘写回均保留该快照；浏览器将已有提交意图的快照传给队列，并在恢复核对时比较它。草稿和队列共用同一份严格校验器，避免字段规则漂移。

运行启动尚未接通原子应用：带快照的队列项在启动前返回明确的 `queue_profile_pending`，不会默默使用会话旧配置。当前页面尚不创建这种快照项，正常旧项仍可执行。下一阶段须把快照从队列的核对与 claim 一起带入独占会话启动，校验图片能力和模型，再开放运行中的选择器。
