# 运行中切换后续消息配置

状态：主要交互链已落地。2026-09-28 对照 `app_bak/wwwroot/src/ui.js` 的输入区和当前单文件版，完成草稿、提交意图、队列项的配置快照，绑定运行的原子应用，以及运行中选择器和隔离打包页验证。实体移动设备与原生 WebView 仍待验收。

## 现状与目标

旧版在当前任务运行时保留模型、思考强度和权限入口，选择模型还会更新所选会话的配置。实施前的 `app/web/js/features/chat/composer-profile.js` 在 `runActive` 时禁用三个入口；隔离单文件 Home `.build/mdo-packed-docks-bpncv2lo` 在 390×500 运行 `SLOW UI` 时确认输入仍可编辑、三个选项均为 disabled。服务端 `MdoSessionSetProfile` 要求会话处于 active 且 idle，因此运行中的选择要保存为后续意图。

恢复后的行为应当是：当前运行继续使用启动时的配置；用户运行中调整输入区选项，看到明确的“下次任务生效”状态，可以继续输入与排队；每条待发送消息在提交时冻结其模型、思考强度和权限，后续调整不改写已经入队的消息。刷新或切换会话后，尚未发送的选择与每条消息的配置仍可追溯。无效模型、能力不兼容及配置保存失败应明确报错并保留原消息，不得静默回退到别的模型，也不得提前改写历史。

## 持久化与协议边界

1. 会话草稿保存“下一条消息的配置选择”；提交意图保存同一配置快照。`draft.json` 已升至 schema 7，继续读取旧文件，新增字段有长度、枚举及完整性校验。选择存于便携 Home，而非浏览器 `localStorage`。
2. 队列项保存不可变的配置快照。`queue.json` 已升至 schema 7；旧项没有快照时沿用当前会话配置。队列 POST 的同 ID 幂等比较包含配置，避免另一页面用同一 ID 改写将要执行的模型或权限。队列 GET 返回快照，供页面显示和核对。
3. 对绑定队列项的运行，服务端须在独占会话启动的同一事务边界内检查队列快照、校验模型能力、应用有效配置并开始运行。浏览器先 PUT 会话 profile、再 POST run 的两步方案有竞态：另一个标签可能在两次请求之间启动不同队列项。图片能力必须按该项的有效模型判定。运行已被接受后的凭据仍按现有 `starting`/`accepted` 规则处理。
4. 会话运行中调整的配置只作为后续意图保存，不能改变运行中的 Agent。没有排队项时，新选择仍保留在会话草稿；会话空闲后可通过已有 profile API 落地，或者在下一次绑定运行时原子应用。界面必须区分会话当前配置和后续意图，不能把尚未落地的选择呈现为已完成更新。
5. 跨标签提交沿用已有草稿 revision、稳定提交 ID 和核对屏障。同一队列项只能执行其冻结配置；不确定响应不得通过更换 ID 或模型自动重试。新任务的首次提交需要继续把创建时的 Agent、模型、思考强度、权限一起固定。

## 实施顺序与验收

1. 先扩展草稿、提交意图与队列的读写合同，含旧 schema 迁移、严格验证、幂等冲突和配置缺省测试；保持当前 UI 禁用直到服务端运行边界完成。
2. 将配置应用纳入绑定队列项的服务端启动流程，覆盖不同标签同时发现队首、不同配置的连续两项、运行忙碌、启动前明确失败与启动结果不明。任何失败都不得让后续项抢跑。
3. 再开放前端运行中的三个选择器，显示后续生效状态，持久化选择并在提交时快照；切会话、刷新、归档只读状态和 `/model` 命令须一致。
4. 用生产模块浏览器夹具及隔离单文件 Home 验证一条运行中、两条不同配置排队消息的最终运行记录和页面回放；检查服务端队列、草稿、凭据、浏览器脚本错误和单文件零旁路写入。Windows/Linux 仅做有界发布门禁，不做压力或高负载测试；原生移动端另行验收。

事务边界完成后才解锁了运行中的前端选择器。

## 第一阶段：草稿与提交意图

`draft.json` 已升级为 schema 7，并继续严格读取 schema 1–6。可选 `composer_profile` 保存下一条消息的完整模型、思考强度和权限选择；PUT 未提供该字段时保留原值，显式 `null` 清除。每条 `submissions` 的可选 `profile` 是完整且不可拆分的快照，携带该字段的重复 ID 仅在配置相同的情况下视为幂等。浏览器草稿存储往返保留这些字段，且加载前先编辑文字不会擦掉远端已保存的选择。旧数据没有快照时仍保持原 API 响应形状。

第一阶段只建立草稿持久化合同；队列传递见下节。运行中的选择器到第四阶段才解锁。

## 第二阶段：队列快照

`queue.json` 已升级为 schema 7，仍读取 schema 1–6。队列 POST 的可选 `profile` 必须是完整三字段对象；相同 ID 若模型、思考强度或权限不同，返回 `queue_id_conflict`。队列 GET、状态转换与磁盘写回均保留该快照；浏览器将已有提交意图的快照传给队列，并在恢复核对时比较它。草稿和队列共用同一份严格校验器，避免字段规则漂移。

第二阶段结束时，运行入口以 `queue_profile_pending` 阻止快照项按旧配置执行；第三阶段已移除这道临时保护并接通原子应用。第四阶段才让页面把输入区选择冻结为提交快照，并解锁运行中的三个选择器。

## 第三阶段：绑定运行的配置应用

队列 prepare 在锁内读取快照，claim 在同一项上复核文本、附件和快照，防止两次请求之间被另一标签替换。运行入口按快照模型预检图片能力，把完整配置传给运行管理器；会话打开时先取得独占运行预约，再用所选配置创建 Agent、核对恢复状态并提交有效会话元数据，随后才开始运行。不存在的模型或启动前明确失败会释放 claim，保留原队列项；已接受运行仍使用原有凭据规则。旧队列项没有快照时沿用当前会话配置。

真实 HTTP/TCC 探针让同一会话连续执行高思考只读、普通思考平衡两条快照项，运行记录与会话元数据分别反映该项配置；再新增指向本地模型夹具的第二模型，由队列项切换后成功运行，证明模型选择也进入实际 Agent。不存在的模型返回 `session_profile_invalid`，无运行凭据且元数据未变；双客户端同时争抢带快照的同一项仅接受一次。前端选择与单文件页面回放见第四阶段。

## 第四阶段：运行中选择与可追溯队列

会话运行时，模型、思考强度与权限仍可操作，变更先写入该会话的便携草稿，不调用要求 idle 的会话 profile API。输入区显示“下次任务生效”；切换会话或刷新后从草稿恢复。发送时把当时三字段复制到提交意图，入队后队列卡显示“已固定：模型 · 思考强度 · 权限”，后续更改不会改写已有卡片。空闲时仍通过原 profile API 直接更新会话；若存在旧的后续选择，在成功更新后清除并持久化。新任务首次及后续待发消息也保存各自快照；确定性创建失败时，用户审核的新配置会一起替换尚未创建的任务及其待发快照。

生产模块浏览器夹具 `tests/fixtures/composer-profile-deferred-browser.html` 验证运行中可选择、仅写草稿、另一个草稿实例重新加载、切换会话隔离、返回恢复、空闲直接更新；既有跨会话异步 profile 夹具回归通过。隔离单文件 Home `.build/mdo-packed-docks-f9e1l7aw` 在 390×500 实测慢速运行时三项可选、状态和冻结配置卡片均在视口内，选第二模型/高思考/只读后排队运行；运行记录依次为原模型中思考、第二模型高思考、原模型中思考。浏览器脚本错误为空。

单文件 Home `.build/mdo-packed-docks-eye7nuqn` 在同一慢速运行中同时保有两条不同配置的待发项：队列 API 与页面卡片分别为第二模型/高/只读、原模型/中/询问。刷新后两张卡仍保持各自快照，随后三次运行依次按原模型中思考、第二模型高思考、原模型中思考完成，队列清空。双标签 Home `.build/mdo-packed-docks-nt_ms6y6` 则发现一个呈现问题：草稿 revision 冲突虽已提示“草稿未保存”，后续配置标签仍称“下次任务生效”。现根据草稿 profile 的保存状态分别显示保存中、已保存后续生效、后续配置未保存；单文件 Home `.build/mdo-packed-docks-5b7eg_vp` 复测第二标签明确显示“后续配置未保存”，服务端保留第一标签的配置，刷新后第二标签恢复该已保存选择，浏览器无脚本错误。跨标签冲突目前需刷新后复核；实体设备与原生 WebView 尚未验收。
